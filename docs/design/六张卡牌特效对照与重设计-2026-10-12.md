文件 KarenWeKnow.cs 中类型拼写为 KarenWeKown，光辉文件 KarenWeKonwToken.cs 中类型为 KarenWeKownToken。这里保留源码实际名称，避免按相似名字接错牌。

这些效果中，只有蛋糕是 Skill，另外五张均为 Power。它们都属于收益/生成/协作表现；不用套储君攻击牌的伤害方向和强冲击。

## 3. 对照结论：当前方案哪里需要提升

下面是对代码、选定方案及 HTML 代表帧的判断，不是对 Banana 实机录像的逐帧验收。

| 卡牌 | 当前已做对的部分 | 需要提升的部分 | 储君可借鉴的案例 |
| --- | --- | --- | --- |
| 蛋糕 | 成瓶 → 原生药水飞行已经精确交接；按 PotionModel 限定，满栏区分 | 细屑太平均容易像通用金粉；成瓶前的体积变化还可以更有主次 | Alignment 的资源聚集、Solar 的起点/落点分工 |
| 什锦 | 后层烟与前层暖光分离；增益脉冲监听真实力量 | 什锦与晚餐在代表帧都像三束金光，临时/永久的运动差异不足 | Resonance 的状态变化、Radiate 的起势与短确认分离 |
| 晚餐 | 三束暖辉依次出现；不留下常驻烟/环 | 与什锦共用较多主体结构，差别偏向时间和浓度 | Pillar 的默认/激活层分离；Genesis 的一次施放取舍 |
| 门票 | 粒子携带真实塔牌，塔库存不变；层数错开发放 | 多方案仍主要差在粒子颜色与路线；当前起势和散开占用较长，派牌动作不够突出 | BigBang 的一次母演出；Lunar 的可数单位 |
| 梦想 | 两源汇合、每层一张光辉、接入既有库存星 | 暖冷流与门票的汇聚/扩散同构；交汇很亮时易成为通用爆点 | SevenStars 的数量关联、Supermassive 的同一对象交接 |
| 一起闪耀吧 | B 脚灯有队伍空间关系；每人确认战后奖励 | 按队友重复灯束可能像逐个加力量；标记与奖励的关系需更清楚 | 群体主体一次 + 每目标小反馈；Pillar 的触发与状态分工 |

当前问题主要是**母动作趋同**，并非简单缺少粒子。门票、梦想堆到上千枚 Canvas 粒子仍可能长得像同一团金粉；什锦、晚餐同时亮三束也容易撞型。

重设计先区分“粒子为什么这样运动”，再用粒度、色彩、层级和寿命增加质感。

## 4. 统一风格与六个主动作

| 卡牌 | 唯一主动作 | 主色与颗粒 | 视觉重心 |
| --- | --- | --- | --- |
| 蛋糕 | 糕屑从松散到内收，凝成药水 | 金棕粗屑 + 少量奶白细光 | 角色侧面的成瓶点 |
| 什锦 | 暖汽快速上涌，获得力量后通风散开 | 浅琥珀柔汽 + 短暖白细屑 | 脚下 → 身体两侧 |
| 晚餐 | 重一些的金屑缓慢上升，三次暖辉递进 | 蜂蜜金 + 柔奶白亮点 | 身体中下部，不遮脸 |
| 门票 | 舞台金尘卷起，真实卡牌依次派发 | 暖金小点 + 少量绯红短片 | 身侧生成区 → 真实手牌目的地 |
| 梦想 | 两股暖冷体积粒子同拍汇合，再送入库存 | 暖金 / 冷白，两源到一源 | 身体两侧 → 交汇点 → 约定入口 |
| 一起闪耀吧 | 同一排脚灯推进队伍，再逐人确认标记 | 暖金脚灯 + 短白确认点 | 队伍地面 → 各自奖励标记 |

统一素材：原版 smoke_vfx、ash_particle、PowerUp sparkle/beam/glow；Karen stage_light / stage_light2；真实药水图、塔牌图和库存星节点。低对比烟在后层，短亮细节在前层，真实对象走已有视图系统。

默认六张均不用全屏曝光、强震屏、巨大屏幕扭曲。区别来自动作和局部亮度峰值；与已有约定塔、火焰、穿身环叠加时，应优先让身体和目的地可读。

## 5. Banana蛋糕 A：糕屑聚瓶，重设计为“粗屑内收 → 一瓶接力”

### 5.1 新时间线

| 正常速度建议时间 | 动作 | 规则 / 交接 |
| --- | --- | --- |
| 0.00–0.12 s | 角色侧面松散出现金棕糕屑；大颗粒低亮，少量奶白点先行 | 只表达制作起势 |
| 0.12–0.32 s | 颗粒沿不同弯曲路线内收，中心缩小；尾迹短且不描闭合圆 | 成瓶点跟随角色坐标 |
| 0.32–0.42 s | 2–3 片短烟交叠；粗屑明显减少，中心一记局部短闪；实际药水图显现 | 保留当前 0.42 s 原命令节点 |
| 命令成功后 | 成瓶处停止绘制占位图；这一瓶药水由原生 AnimatePotion 飞入药水栏 | 同一 PotionModel，接力点一致 |
| 命令失败后 | 只留松散糕屑与薄烟向下散开，药水图约 0.25–0.35 s 淡出 | 不飞入栏、不亮成功星 |
| 1.10–1.25 s | 剩余气味般细汽退场 | 新节点归零 |

### 5.2 与原方案的具体差异

把原来近似均匀的 64 枚内收细点分成粗屑、细屑、亮点三种尺寸。粗屑较慢、路径短、透明度低；细屑负责最后的速度变化；中心短闪只占一次。

主体仍是用户选定 A，不画蛋糕模型、纸托、瓶形粒子轮廓或魔法阵。唯一实体是需要交接的实际药水图。

### 5.3 实现约束

沿用已有 KarenBananaCakePotionVfxPatch 和具体 PotionModel 原点映射；不改成功/失败规则，不额外调用 PotionCmd。不增加第二个飞瓶节点。视觉取消后原命令继续，finally 清除映射。

这项改动可主要调现有 Burst/Puff 的分组和时间包络，不必替换已通过专项的药水取得接线。

## 6. Banana什锦 A：沸汽升腾，重设计为“快升 → 短确认 → 散热”

### 6.1 打出时间线

| 建议时间 | 动作 | 规则 / 交接 |
| --- | --- | --- |
| 0.00–0.16 s | 两片后层暖汽从脚底偏左右出现，中心留出身体 | 薄、宽、快速上升 |
| 0.16–0.40 s | 汽上升至腰肩，两侧细屑加速；只有低亮暖色 | 保留当前临时力量命令起点 |
| 实际 Strength 增长时 | 一束短暖白主束与两侧极细亮点同时脉冲，峰值约 0.10 s | 以 WatchStrength/CheckStrength 确認 |
| 确认后 0.10–0.45 s | 汽向左右通风散开；暖金转低饱和灰琥珀，短屑很快退出 | 用“释放、散热”区分暂时力量 |
| 约 1.10–1.20 s | 后层最后薄汽消失 | 没有新常驻状态物 |

**关键变化：** 三根同等宽度金束改为一记很短的主束和轻辅助点；最大的体积放在向上升腾的烟里。临时力量通过快速获得、快速散开表达，与晚餐的缓慢递进区分。

### 6.2 约定牌堆内变牌：单独的小演出

当 OnTurnEndInPromisePile 执行 CardCmd.Transform 时，沿用现有真实卡预览和替换流程：

~~~text
旧什锦卡出现
→ 卡面边缘少量暖汽内收（可选新辅助层）
→ 原生 Transform Shine 遮住切换
→ 真实晚餐卡显现
→ 同一卡牌替换完成，库存视觉按项目已有机制接续
~~~

此时**不亮力量光束、不出 +8/+10、不表现角色已经吃下晚餐**。变牌只改变卡牌，力量在晚餐真正打出时才增加。

这条是新的设计建议，Banana 当前专项没有实现或验证新变牌层。建议先保留原生 CardCmd.Transform，再决定是否添加很小的粒子辅助。

## 7. Banana晚餐 B：餐后暖辉，重设计为“缓升 → 三拍暖辉 → 稳定退场”

### 7.1 新时间线

| 建议时间 | 动作 | 规则 / 交接 |
| --- | --- | --- |
| 0.00–0.22 s | 脚下暖汽低而薄；蜂蜜色小屑从下半身附近缓升 | 整体速度比什锦慢，颗粒稍重 |
| 0.22–0.51 s | 细屑向身体中部内收，背景暖光面积增加但峰值受限 | 保留当前永久力量命令起点 |
| 实际 Strength 增长后 | 三束暖辉按 0.06 s 间隔依次点亮，中间最后收束成暖白 | 同一次增长，只是三拍视觉 |
| 确认后 0.18–0.65 s | 金屑继续缓慢上升，暖辉逐根退；短余亮停在腰胸附近 | 不新增数值飘字 |
| 约 1.25–1.40 s | 暖汽与余亮都退场 | 永久力量留在模型，视觉不常驻 |

### 7.2 与什锦的对照

| 项目 | 什锦 A | 晚餐 B |
| --- | --- | --- |
| 主体 | 宽薄暖汽 | 金屑与暖辉 |
| 起势速度 | 快升 | 缓升、内收 |
| 确认节拍 | 一次短脉冲 | 一次收益对应三拍光 |
| 退场方向 | 两侧散开、冷却 | 原地温和变暗、缓慢上升 |
| 常驻物 | 无 | 无 |

永久数值不需要永久大光环；“更稳、更饱满”的余韵足够。保留玩家选定 B，主要改现有 DrawMotes/DrawLights 的粒度和包络，不改力量命令。

## 8. 门票：收敛为“金尘卷幕 → 逐卡派发”

### 8.1 初次打出能力

0.00–0.18 s 身侧暖金微尘卷起；实际 Power 施加成功后，短束向能力图标方向退散，一次局部闪亮确认。约 0.70–0.85 s 完成。

首次施放不生成假塔牌、不增加塔库存。升级固有只影响开局拿到这张牌，不把特效改成大招。

### 8.2 每回合触发

| 建议时间 | 动作 | 真实模型关系 |
| --- | --- | --- |
| 0.00–0.18 s | 一簇后层金尘从身侧向上卷，绯红粒子只作少量点缀 | KarenTicketPower.Flash，开始本次生成 |
| 0.18–0.36 s | 粒子流压窄，在手牌附近的原生生成区形成亮核 | 即将显示本次实际 CardModel |
| 第一张约 0.36 s 起 | 每张塔牌沿原生生成/入手流程出现，短粒子尾迹跟随；卡间建议 0.08–0.10 s | 不手工摆假手牌，不接管排序 |
| 到达实际目的地 | 尾迹收短，原生命令给到达反馈 | 如手牌满，按真实规则落点调整，不强行画进手牌 |
| 单层约 1.05–1.20 s | 主尘流结束，低亮余尘退场 | 约定塔库存不变 |

### 8.3 为何区别于梦想

门票是**一条派发流**：金尘为牌让路，真实卡牌一直是视觉主角。梦想是**两股能量共同形成一个入堆单位**，小库存星才是终点。

旧预演回合触发约 1.85 s；新方案压缩起势，优先让实际塔牌在较早阶段出现。以上时间是待实机校准参数，不通过人为延长 BeforeHandDraw 阻塞整次正常抽牌。

## 9. 两人的梦想：收敛为“双流同拍 → 光辉接入原有库存星”

### 9.1 初次打出能力

两股粒子从角色身体左右起，暖金与冷白分开，向中部低亮汇合。实际 Power 成功施加后，一次短共鸣亮点退向能力图标；约 0.85–1.00 s。

不立刻增加光辉，不立刻回能，不为两个源头画新角色、双手、饰物或几何徽章。

### 9.2 回合末触发

| 建议时间 | 动作 | 真实模型关系 |
| --- | --- | --- |
| 0.00–0.22 s | 左右两片松散体积粒子同时上升；中心保留空隙 | 不画对称硬曲线轮廓 |
| 0.22–0.38 s | 两片收拢，暖冷在交汇点混成奶白短闪；外侧立即降亮 | 本次 AddToken 的实际卡牌开始可视化 |
| 约 0.38 s 起 | 每张光辉由现有 PromisePile 生成/运输链路派发；混色尾迹由粗到细 | 绑定具体 CardModel |
| 到达约定入口 | 在同一位置交接给该牌现有库存星，短闪后回到正常库存亮度 | 不复制第二颗假星 |
| 约 1.20–1.40 s | 两股源头和运输余迹全部退出 | 库存只增加真实生成的 Amount 张 |

### 9.3 层数与空虚入口

三层共用一次双流起势；每层一张光辉，建议错开 0.10 s。高层数时限流的是新粒子背景和音效，不是实际卡/星数量。超多层可缩短单卡间隔、合并共同确认声，不延长成 N 次完整大演出。

目的地使用已有约定塔/空虚入口坐标服务。空虚模式下从同一个生成事件接到左下入口，入口变化时获取当前目的地；不写死预演的屏幕坐标。

与储君 ReturnAllStars 的“销毁再按数量重建”不同，Karen 的库存星继续按具体卡牌身份管理。连续性优先于再加一个更亮的终点爆炸。

## 10. 一起闪耀吧 B：同台脚灯，重设计为“一次铺灯 → 逐人确认”

### 10.1 新时间线

| 建议时间 | 动作 | 实际事件 |
| --- | --- | --- |
| 0.00–0.22 s | 一排低亮脚灯从施放者向队伍另一端推进；用柔光贴图，不画硬金线 | 全队共享起势一次 |
| 0.22–0.46 s | 各玩家地面灯向身体后方短暂拉起，角色前方留空 | 真实 Player 列表决定位置 |
| 各奖励标记确认后 | 一枚短光点从身体下方接到各自 KarenShineCardRewardPower 标记，局部亮一下 | 以 AddShineCardReward 的本次结果为准 |
| 最后一位确认后 | 一次轻和弦，全排灯共同降低亮度；每人余辉错开消失 | 不按人数重播和弦 |
| 2 人约 1.20–1.40 s；4 人约 1.40–1.60 s | 灯与运输余迹退场 | 能力标记保留，实际卡牌战后发放 |

B 的脚灯方向保留。加强“共同起势”的空间联系，削弱看起来像逐个加力量的身体光束。各玩家是各自的奖励落点，不给队友画 Karen 专属塔或光辉库存。

### 10.2 多人边界

共享演出由具体出牌事件启动一次，按 Player/NetId 找到各节点。规则仍由已有命令执行。不能复制储君仅 LocalContext.IsMe 的单人星环控制器后，就宣称队友也有对应视觉。

队友掉线、死亡或暂时没有 NCreature 视图时：保留原有奖励规则，仅跳过该玩家画面；不把“没有画出来”当成“没有获得奖励”。

当前 HTML 的 2/3/4 人排布是比例示意，新预演也没有完成联机同步验证。

## 11. Godot 制作建议：共享流程，单卡配置差异

这轮重设计不需要给六张牌各造一套完全独立系统。建议共用四个阶段，分别配置：

~~~text
起势（可立即播放的主题层）
→ 命令执行（已有模型逻辑，只调用一次）
→ 结果确认 / 实体交接（按结果、CardModel 或 Player 身份）
→ 余韵清理（正常结束、取消、退出战斗均可完成）
~~~

| 部件 | 适合实现方式 | 原因 |
| --- | --- | --- |
| 粗细屑、松散微尘 | 小纹理程序绘制或 GPUParticles2D | 数量、方向、大小可调 |
| 体积暖汽 | 原版短翻页 + 随机缩放旋转 + 透明度曲线 | 保留游戏烟雾质感 |
| 局部短闪 | 原版 Sparkle / 小 Glow，实例参数 | 只在确认点强调 |
| 舞台灯 | 现有 Karen 舞台灯节点/纹理 | 统一角色主题 |
| 药水运输 | 现有具体药水原点补丁 + 原生 AnimatePotion | 已有正确接线，保持身份 |
| 入手塔牌 | 原生 AddGeneratedCardsToCombat 视图 | 处理手牌上限、排序等 |
| 光辉入堆 | 现有 PromisePile 每卡一星链路 | 维持对象连续性 |
| 常驻状态 | 原有 Power 图标 / 库存星 | 六张不新增常驻巨大光物 |

以上素材选择是实现建议。Canvas 预演不能证明 GPU 粒子预算、HDR 或 Godot 光效等价。

### 11.1 起步预算与亮度规则

可从以下概念预算试做，不作为性能验收：

- 每次起势 40–100 枚低亮颗粒，10–30 枚主体细屑，2–6 枚短 Sparkle；多层共用起势。
- 体积汽先试 6–12 个小烟片，避免长时间大面积透明重叠。
- 每卡/每玩家运输另有少量跟随颗粒，密度随层数平方根下降；真实对象数量保持不变。
- 同一时刻只有一个最亮区域。人物脸、卡牌标题、手牌和收益目的地周围不铺大白光。
- 末帧新增烟、光束、粒子节点应为零；只有真实能力图标与库存状态留下。

Rich 粒子模式可提高辅助数量，保持主体尺寸和关键节拍不变。低特效模式保留主方向、真实卡/瓶与成功确认。

### 11.2 声音与速度

| 卡牌 | 新主题声设想 | 与原生声音的关系 |
| --- | --- | --- |
| 蛋糕 | 短颗粒聚合 / 轻成瓶 | 入栏继续原生，失败不用成功音 |
| 什锦 | 很短暖汽起势 | 真实增益声为峰值，避免再叠三次 |
| 晚餐 | 温和起势，三拍视觉共用一个增益确认 | 不按三束光重复力量音 |
| 门票 | 轻短卷幕 / 细屑派发 | 原生卡生成声为主，多层节流 |
| 梦想 | 暖冷两音到一音 | 每批一次共鸣，库存交接轻响 |
| 一起闪耀吧 | 脚灯推进弱起音，最后一个共享和弦 | 单个标记反馈保持轻 |

尚未选择或新增音频资产，HTML 默认无声。优先试项目已有声音，再决定是否需要用户提供合法音源。

Fast 按项目已有速度策略缩短时间；Instant/NonInteractive 跳过新增视觉和视觉等待，实际规则照常。省略演出不影响获得药水、力量、生成卡和奖励。

## 12. 验收与交付状态

本轮应完成：储君分类 MD、六张对照 MD、可拖时间轴的重设计 HTML。新 HTML 使用原版/Karen 原有素材编排；各张表现语法可见，不只给方案命名。

实装时按以下项目做针对性验证：

| 牌 / 场景 | 必要验证 |
| --- | --- |
| 蛋糕 | 成功 / 满栏、基础 / 升级；原点一致；一瓶、一次飞行；取消仍执行规则 |
| 什锦 / 晚餐 | +8/+10；下一回合临时扣回、永久保留；变牌不加力量；真实增长才确认 |
| 门票 | 1/3 层；生成实际卡；手牌满按真实结果；塔库存不变 |
| 梦想 | 1/3 层；普通/空虚入口；每卡一星；生成时不回能；运输后节点一致 |
| 一起闪耀吧 | 实装后做相关同版本多人专项；2/3/4 人位置；每人标记与战后奖励一致 |
| 通用 | Fast/Instant；连续出牌和额外重播；镜像/缩放；已有火焰/环；退出和取消清理 |

涉及移牌的实机检查必须通过 KarenSTS2MCP 保存前后截图，动画结束运行 karen_check_hand。正式版和测试版分别记录通过/失败/未测；不自动扩展为完整测试矩阵。

Banana worktree 已记录的双版结果属于**旧选定方案的现有实现**；不能拿来证明本次新节拍已通过。门票、梦想、一起闪耀吧和新变牌辅助层仍是设计阶段。
