# 原版卡牌特效制作参考

> 更新：2026-09-30。用途：制作 Karen 新卡特效时，按表现需求找到原版实现、场景结构、触发时序及复用边界。

本体特效最值得学习的是**将动作、飞行、命中、状态残留和结算反馈拆开，再用明确的时序组合**。一张卡没有专属 VFX 类，也可能通过攻击命令、Power、球、卡牌通用流程得到完整表现。查资料时应沿着「卡牌 → 命令或关联模型 → 节点 → 场景 → 材质与纹理」阅读。

## 3. 原版如何把一次出牌拼起来

### 3.1 卡牌流程与自定义演出的分工

[CardModel](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Models/CardModel.cs) 的 `OnPlayWrapper` 管理手动/自动打出、能力牌飞出、重复播放及结算牌堆等通用流程。新卡通常只需要定义自己的 `OnPlay` 和必要的视觉入口。

`OnEnqueuePlayVfx` 在真正 `OnPlay` 之前启动，适合预备动作和纯视觉。它不是结算保障点，不应承担伤害、抽牌、回能或随机目标选择。`Hellraiser` 就把入队演出和施加 Power 分开。

不要为了「看起来卡已经抽到了」自行创建手牌卡节点。游戏状态、真实卡视图和排序应继续由原生命令以及 Karen 已有移牌系统管理。

### 3.2 攻击命令的关键时序

参照 [AttackCommand](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Commands.Builders/AttackCommand.cs)。以下省略取消、目标检查和其他 Hook，只展示制作时最容易用错的相对顺序：

```text
每一击：
  攻击者特效 / 声音 / 动作 / AfterAttackerAnim
  命中声音
  WithWaitBeforeHit 指定的等待
  自定义命中节点、命中场景
  BeforeDamage
  CreatureCmd.Damage（真实伤害及通用受击反馈）
```

- `WithAttackerFx(...)`：出招方效果；`WithAttackerAnim(...)`：出招动作及延迟。
- `WithHitFx(...)`：命中场景与声音；`WithHitVfxNode(...)`：需要目标参数或自定义节点时使用。
- `WithHitVfxSpawnedAtBase()`：场景位置从默认 `VfxSpawnPosition` 改为角色节点的 `GlobalPosition`。它不等价于任意模型的碰撞盒底部。
- `SpawningHitVfxOnEachCreature()`：让群攻命中场景逐目标生成；否则群攻可以在敌方区域中心生成一次。
- `WithHitVfxNode(...)` 的工厂会收到具体目标，适合每个目标各有冲击。
- **`OnlyPlayAnimOnce()` 只影响攻击者一侧的动画、特效、声音和 `AfterAttackerAnim`。命中声音、命中特效及 `BeforeDamage` 仍可每击执行。** 把一次性全屏演出放进 `BeforeDamage` 再配多段攻击，会反复创建。
- 命中声音在 `WithWaitBeforeHit` 之前，因此这个等待不能用于保证声音与自定义投掷物落点严格同步。

`CreatureCmd.Damage` 已包含伤害数字及相应的受击、格挡等反馈；`CreatureCmd.GainBlock`、`CreatureCmd.Heal`、`PlayerCmd.GainEnergy` 也有原生表现。自定义层应该增加主题表达，避免再播一套相同的基础收益提示。

Karen 攻击卡使用已有 [AttackCommandCompat](../src/Core/Compat/AttackCommandCompat.cs) 的 `FromPlayedCard(this, cardPlay)`。正式版 `FromCard(card)` 与测试版 `FromCard(card, cardPlay)` 的签名不同，不要把测试版反编译示例原样粘贴到双版本代码。

## 4. 最值得拆解的完整案例

### 4.1 弹跳药瓶：投掷 + 飞溅 + 残留

源码：[BouncingFlask](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Models.Cards/BouncingFlask.cs)、[NItemThrowVfx](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Nodes.Vfx/NItemThrowVfx.cs)、[NSplashVfx](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Nodes.Vfx/NSplashVfx.cs)。

它先播放 `Cast`，用战斗目标 RNG 决定本次真实目标，再把药瓶纹理从起点抛向目标碰撞盒底部。随后叠加飞溅、液体覆盖和气体冲击，最后施加中毒。下一次投掷从上一目标附近继续。

`NItemThrowVfx.Create(sourcePosition, targetPosition, itemTexture, scale)` 接受纹理，所以这种模式很适合皇冠、硬币、碎片等实体。场景用三条 Curve 控制水平进度、抛物线高度和旋转；美术运动不需要和结算逻辑写在一起。

需注意：原卡等待 `0.5s`，投掷场景的 `_flightTime` 是 `0.55s`，这不是精确的「等待落地事件」。新制作需要严格对齐时，应让自己的演出控制器提供明确的命中时点/等待任务，并统一处理游戏速度，不能把这个常数当通用公式。

飞溅节点将液滴与液面飞溅子场景组合，统一染色并重启粒子；随后等待残留消失并释放。它同时演示了退出场景时取消异步等待的处理。

### 4.2 陨石打击：先让观众看懂飞行，再结算

源码：[MeteorStrike](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Models.Cards/MeteorStrike.cs)、[NLargeMagicMissileVfx](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Nodes.Vfx/NLargeMagicMissileVfx.cs)。

卡牌创建大型飞弹，等待节点给出的 `WaitTime`，然后攻击并生成等离子球。节点内部拆成预备、飞行、载荷和命中粒子，冲击后保留一段残留，再清理。

可借鉴的是「节点管理演出，卡牌管理结算」。不要让特效节点自己扣血，也不要因为节点创建失败而跳过卡牌效果。强震屏、长拖尾和大粒子适合强调高强度冲击；作为所有普通技能的默认配置会掩盖信息。

### 4.3 超能光束与华丽收场：群攻主体只有一个

源码：[Hyperbeam](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Models.Cards/Hyperbeam.cs)、[GrandFinale](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Models.Cards/GrandFinale.cs)。

`Hyperbeam` 用一次横向光束连接施法者与敌方范围，在各敌人身上分别补冲击节点；光束在伤害前留出时间。改写时要处理没有有效敌人、目标提前死亡、敌人布局变化等分支。

`GrandFinale` 先创建主演出，等待 `totalAnticipationDuration`，再做群体攻击并逐敌人产生冲击。这个结构很适合「聚光 → 大动作 → 同步爆发」，比在每个目标身上重复整段全屏演出更清楚。

### 4.4 旋风斩：持续层与多段命中分开

源码：[Whirlwind](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Models.Cards/Whirlwind.cs)。

X 大于零时创建横向速度线与烟雾暗角，再执行多段攻击。持续时间考虑 X 和快/普通速度，并限制用于背景时长计算的 X 上限。背景表达持续旋转，命中斩击表达每次伤害。

新多段特效应先决定「整张卡出现一次」和「每击出现一次」分别有哪些层，再选择创建位置。额外重播是另一轮出牌，也要单独验收，不能简单用全局静态标记屏蔽第二次。

### 4.5 能力与形态：跟随模型生命周期

源码：[EchoFormPower](../artifacts/vanilla-vfx-audit/beta/MegaCrit.Sts2.Core.Models.Powers/EchoFormPower.cs)。

测试版的回响形态由 Power 持有特效引用：施加时创建，移除时停用，回合开始恢复可用状态，并随实际触发情况改变视觉。卡牌的 `OnPlay` 只是入口。

这些形态基于 `NFormVfx` 与角色 Spine 身体结构。Karen 是否能直接使用，取决于其角色视图、骨骼与材质结构；仅有同名角色动作并不足够。而且这些新形态节点在正式版不存在。适合学习生命周期，不能直接当成双版本通用 API。

## 5. 场景、纹理、粒子和 Shader 怎么分工

原版效果经常由多个节点和资源组成；只读 `.cs` 会漏掉大量实际画面参数。打开[场景索引](reference/vanilla-vfx-nodes.md)后继续查看 `.tscn` 的 `ext_resource` 和 `sub_resource`。

| 层 | 负责什么 | 制作时优先调整 |
| --- | --- | --- |
| Sprite2D / 贴图 | 皇冠、刀刃、火焰主体、烟团等形状 | 轮廓、透视、透明边缘、锚点、明暗层次 |
| GPUParticles2D | 火星、液滴、烟尘、短命碎片 | 数量、方向、初速、重力、寿命、尺寸与颜色渐变 |
| 子场景 | 可独立复用的飞溅、冲击、拖尾 | 起播时间、位置、大小、前后遮挡 |
| Curve / Tween / AnimationPlayer | 位移、旋转、缩放、透明度、阶段切换 | 加减速、停顿、冲击瞬间、收尾 |
| Shader / ShaderMaterial | 溶解、扰动、遮罩、流动、发光 | UV、时间、阈值、颜色和混合方式 |
| C# 控制器 | 绑定对象、设置参数、触发阶段、释放 | 创建契约、取消处理、节点有效性与结算对齐 |
| 音效 | 材质、动作和冲击的听觉提示 | 同步时点、次数、响度、距离感 |

实践建议：先让静态轮廓和空间关系成立，再加运动与粒子。复杂熔池、金属或烟火质感更适合贴图、材质和分层粒子；大量 `_Draw()` 多边形适合简单图形，但不会自动获得原版的材质细节与边缘变化。

反编译的 Godot C# 文件还包含生成的 `PropertyName`、`MethodName`、序列化和方法绑定代码。阅读业务方法及 Export 参数即可，不要把这些生成代码复制进新节点。

## 6. 新节点必须明确的契约

### 坐标与图层

- 角色附近：从对应 `NCreature` 获取位置。`VfxSpawnPosition`、`GlobalPosition`、`GetBottomOfHitbox()` 是不同的锚点，按视觉含义选用。
- 战斗空间：挂到 `CombatVfxContainer`；传入全局坐标后确保没有再被父节点变换一次。
- 全屏层：参照 `Adrenaline`、`Whirlwind` 的挂载位置与本机判断，不能把 UI 像素位置直接当角色世界坐标。
- 多人：区分「所有人都要看到的战斗事件」与「只属于本地玩家的屏幕强调」。后者可使用本机判断；不要因此漏掉远端角色的必要战斗反馈。

### 生命周期与异步

创建失败或无视觉环境时，卡牌效果仍必须结算。原版许多 `Create` 会在 TestMode 返回空；调用方应允许这个结果。

演出控制器建议明确提供开始、命中、收尾和取消四个阶段。退出战斗、节点释放、目标死亡时取消等待并停止后续访问；调用实例方法前确认引用有效。粒子尚未消失时不要立刻移除整个父节点，但也不能让持久节点脱离模型管理。

为每次出牌保留自己的实例。多次触发、额外重播、自动打出与双方同时动作时，共用一个静态「当前特效」很容易串线。纯装饰随机可以独立生成；影响真实目标和结果的随机必须留在战斗模型的确定性流程里。

### 时间与声音

不要同时对时长应用两套速度缩放。明确节点内部使用的时间、卡牌等待与快/普通速度是否一致。伤害或收益应对齐可读的冲击点；烟尘和余辉可在结算后继续自然消失。

原生命令已有的音效先列清单，再决定是否增加主题声。群攻和多段特别容易重复叠加。自定义音频使用项目现有音频通路，检查主音量与音效设置是否只应用一次，避免重复乘音量或绕过用户设置。

## 7. 应用于「向铁水中投入皇冠头饰」

这是制作方案参考，尚未作为最终演出完成或验收。

可以以 `BouncingFlask` 的结构为基础，结合 `MeteorStrike` 的阶段管理以及 `NSplashVfx` / `NFireBurstVfx` 的分层思想：

1. **建立场景**：有透视和明暗层次的熔池/流槽主体，液面与前沿分层。先让人一眼看出这是铁水容器。
2. **投入皇冠**：使用能认出形状的皇冠贴图，从高处沿短抛物线落向明确入水点；旋转只用于增强重量感，避免转得看不清。
3. **接触瞬间**：皇冠下半部被液面/前沿遮挡，短促金属碰撞或熔融声；入水点出现亮核、向外液滴和局部液面扰动。
4. **吞没与反应**：皇冠迅速沉入或溶解，热烟与少量火星上升；不要让皇冠完整停在液面上方。
5. **收益提示**：冲击后执行抽牌、回能；用一次短亮度脉冲强调收益，保留原生抽牌和能量反馈。
6. **退出**：液面、余烟淡出，整个实例释放。再次打出使用独立实例。

重点在可辨识的物件、可信的遮挡、集中于落点的反应，而不是把整屏同时铺满火焰。投掷、液体、火焰节点不必全部直接复用：若原版接口不提供需要的命中回调或材质，可只复用其组织方式，制作 Karen 自己的场景和控制器。

## 8. 双版本与制作验收

已确认的静态兼容差异：

- `AttackCommand.FromCard` 签名不同，使用项目兼容层。

## 9. 如何更新这份参考

工具：[扫描器](../tools/reference/audit_vanilla_vfx.py)、[附录生成器](../tools/reference/render_vanilla_vfx_reference.py)。均为 Python 标准库脚本。先用 ILSpy CLI 对实际两版 `sts2.dll` 完整反编译到 `artifacts/vanilla-vfx-audit/stable` 与 `beta`，再扫描；扫描器本身不会替你完成反编译。

```powershell
ilspycmd -p -o artifacts/vanilla-vfx-audit/stable D:/Godot/Proj/STS2_ShoujoKagekiAijoKaren/artifacts/dev-game/stable/game/data_sts2_windows_x86_64/sts2.dll
ilspycmd -p -o artifacts/vanilla-vfx-audit/beta D:/Godot/Proj/STS2_ShoujoKagekiAijoKaren/artifacts/dev-game/beta/game/data_sts2_windows_x86_64/sts2.dll
python tools/reference/audit_vanilla_vfx.py --sources artifacts/vanilla-vfx-audit --games D:/Godot/Proj/STS2_ShoujoKagekiAijoKaren/artifacts/dev-game --out artifacts/vanilla-vfx-audit/inventory.json
python tools/reference/render_vanilla_vfx_reference.py artifacts/vanilla-vfx-audit/inventory.json docs/reference
```

扫描器只读游戏资源，读取 PCK v3 目录并校验提取文件 MD5，输出特效场景及递归文本依赖；纹理、音频等二进制资源没有在本次文档工作中展开或重新打包。索引采用词法引用分析，不是精确运行时调用图：悬停说明、条件分支和变量都可能产生关联模型引用，需要回到实际 Hook 确认。

提取源码与资源保存在本地 `artifacts/vanilla-vfx-audit/`，不作为 Mod 资源分发。它们不在 Git 文档正文中；新检出目录需先生成审查材料，源码/场景链接才可打开。更新游戏后应在新的输出目录重新反编译，避免旧版残留类混入统计；同时复核主文计数和案例结论。
