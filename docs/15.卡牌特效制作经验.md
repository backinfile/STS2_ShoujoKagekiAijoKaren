# 卡牌特效制作经验

> 整理日期：2026-09-29。适用范围：Karen 卡牌、能力、约定牌堆及相关战斗 UI。
> 本文提炼本轮设计与实装经验，不代表新增功能需求或完整兼容性验收。具体行为以当前代码及最近一次确认的游戏录像为准。

## 1. 先确定玩家要看懂什么

每个特效先用一句话说明：**谁触发、从哪里产生、向哪里移动、什么时刻表示完成、结束后留下什么。** 说不清这句话，就先不要堆粒子。

- 已经认可的特效尽量保留，先优化尺寸、节奏、层级和衔接。
- 独特性来自动作和机制：多轮舞台灯、常驻塔、穿身环、星光重塑，各自有可辨认的行为。
- 不要仅根据卡名自行发明象征物。过去与未来的抽象框架方案曾难以理解，后来收敛为明确的右向左穿身环。
- 优先寻找官方已有视觉、确实看过的 TV 动画片段，以及游戏原生效果。卡图可以证明形状与配色，不能证明运动方向或动画时序。
- 搜到官方链接不等于看到了素材。记录“已观察到的内容”和“设计推断”；无法核实的镜头不要写成官方复刻。

参考记录至少包括：来源、实际可见元素、运动与节奏、采用部分、舍弃部分、证据是否完整。历史参考见 [过去与未来来源选择](design/rare-vfx/past-and-future-source-selection.md)，其中方案取舍应结合后续实现理解。

## 2. 从 SVG 预览到游戏实装

推荐顺序：简要设计 → 来源核实 → SVG 动态预览 → 单个特效实现 → 实机录像 → 根据反馈调整。

SVG 适合验证轮廓、运动、颜色和时序。预览要同时画出人物、塔、牌堆图标和数字，保持接近游戏的相对尺寸；孤立的大特效容易掩盖遮挡问题。

预览最好支持暂停、重播、时间定位，以及能力开关、单次/连续触发。若做多个方案，应比较明确差异，例如传播方向、出生位置、运动节奏；三个近似版本会让人无法判断选什么。

SVG 通过不等于实装通过。真实游戏还涉及坐标变换、遮挡、对象池、移牌完成信号与声音。进入实装后，以真实录屏继续评审。按本轮协作方式，每完成一个特效先交付可观看的录像，再决定下一项。

旧预览和设计笔记可能包含已被否定的方案，应标注历史状态，不能把所有笔记当成同时生效的要求。

## 3. 本轮形成的视觉语言

| 对象 | 主要表现 | 制作时保留的辨识点 |
| --- | --- | --- |
| 约定牌堆 | 人物后方常驻塔与轨道星星 | 塔是稳定空间参照；星星关联具体卡牌 |
| 星光指引 | 与塔内一致的四角星飞入并入轨 | 产生和入轨是连续过程，不在终点换一颗星 |
| 命运舞台的再生产 | 塔脚走灯、向上引导、补牌星星出现 | 让新星有来源，多颗分散出生 |
| 世界上最空虚的人 | 抽牌堆图标原生消耗、塔自上而下传光、星光重塑图标 | 激活后留下淡金偏移轮廓，表达模式持续存在 |
| 过去与未来 | 等大的竖直环从右向左穿过人物 | 出发时间、速度有变化，多次触发可叠加 |
| 我们犯下的罪过 | 分轮舞台灯光与声音，另有 hover 表现 | 舞台节奏和目标感，避免一次性闪完 |
| 燃烧 | 保留已有火焰与强化卡牌表现 | 与其他能力叠加时仍能分辨，不重做整套语言 |

共享形状不妨碍卡牌独特：星光指引、补牌与重塑都使用四角星，但来源、路径、目的和节奏不同。

## 4. 坐标、遮挡和数字要分别处理

### 坐标不能只加减 Position

从卡牌飞到塔、从牌堆图标飞到人物时，使用完整全局变换，再通过目标节点的 `ToLocal` 或逆变换转回绘制空间。只拼接位置偏移，遇到缩小、翻转或父节点缩放就会错位。

明确哪些元素跟随角色尺寸，哪些保持屏幕可读性：环与塔按角色视觉尺寸适配，数字与文字通常需要保持正向、清晰。对不应镜像的竖直环，可提取变换轴长度作为无符号缩放，避免负缩放把运动方向一起翻转。

前后遮挡要用实际场景层级验证。过去与未来的前半环使用人物之后的兄弟节点；把前半环挂在后层节点下面，并不能保证它越过人物显示。原生效果也可能自行重挂节点，不能假定缩放根节点就能控制所有粒子。

### 数字也是完整 UI 的一部分

- 塔顶数字居中应按完整字符串计算，覆盖多位数与模式标记，并留顶部安全空间。
- 数字可使用描边，不必跟随塔的发光一起闪烁。
- 无限模式不显示有限数量；本轮使用 `∞`，叠加空虚时使用 `∞◇`。
- 抽牌堆图标消失或重塑时，同步控制右下角数字与徽章背景，不能只隐藏纹理。
- 保持交互区域，结束或中断时恢复原状态；实际计数继续由游戏逻辑管理。

缩小、翻转、位移、不同体型敌人和 Boss 都属于布局核查场景。它们可以单独验证，不必塞进面向用户的正常效果展示视频。

## 5. 星星衔接：维护一个连续的视觉对象

“丝滑入塔”的关键不只是缓动函数，而是飞行和轨道使用同一个卡牌对应的视觉对象。

1. 按 `CardModel` 关联星星，统一四角星形状、颜色和拖尾绘制。
2. 卡牌进入模型牌堆时，状态同步不能又在终点生成第二颗星。
3. 飞行终点应是到达时刻的轨道位置，不是起飞时保存的静止点。
4. 到达阶段让偏移逐渐收敛，同时考虑速度连续；本轮采用五次插值等方式衔接轨道。
5. 拖尾保留短时间轨迹历史，避免切换状态时旧轨迹突然跳到新位置。

出生位置来自真实卡面变换中心或真实牌堆图标。多张同时进入时，既错开时间，也分配不同轨道相位；仅增加一点延迟，仍可能在同一处堆积。本轮补牌进一步选择较大的轨道空隙安排新星。

批量补牌按批次组织提示与走灯，不为每张卡重复整段能力动画。模式转换的中间状态也不要把已有星星先删除再重新生成。

世界上最空虚的人要求同一批卡在抽牌堆和塔中都有视觉存在，这不意味着复制两份游戏卡牌模型。补牌涉及移除、再加入及事件回调时，还要防重入，避免视觉改造意外引发重复补牌或移除。

## 6. 移牌表现不能接管手牌布局

放入和取出不必强行使用同一套自定义动画。放入可以缩小卡面、接上星星入轨；取出应保留已经自然的原生手牌排布和完成时序。

本轮曾出现“先飞到手牌中间，再移到最终位置”的问题，最终恢复原生取出逻辑，从塔的固定转移锚点进入手牌。额外的中间目标反而暴露了两套布局系统在争夺位置。

改造时保留 `CardPileCmd.Add` 等模型移牌流程，以及适用版本中的 `SwooshAwayCompletion`、`InvokeCardAddFinished` 等完成通知。先分清逻辑归属、节点归属和动画完成由谁负责，再替换视觉部分。

源牌堆信息也可能在原生流程中已经变化，需要依据调用时机使用旧牌堆类型或显式来源参数，不能在模型移动后重新猜测起点。

## 7. 环的调参：尺寸、路程、速度分开

过去与未来最终方向是等大、竖直、右向左穿身；大小变化曾让画面更杂，纵向倾斜也被取消。多个环主要通过出发时间和速度区分。

截至本次整理，当前代码中的关键值如下，仅作为这张牌的经验基准：

| 参数 | 当前值 | 调整目的 |
| --- | --- | --- |
| 横向行程 | `+130 → -130`，再乘自适应单位 | 缩短人物前后距离；旧值为 `±210` |
| 环几何 | `(cos × 48, sin × 92) × 1.52 × unit` | 较前一版放大约 50%，罩住角色 |
| 首环 | `Start=0`、`Duration=1.15` | 取消起步等待，缩短首环穿越时间 |
| 第二环起点 | `Start=0.16` | 更早建立连续穿越感 |
| 淡入比例 | `0.07` | 减少“开始了但看不见”的时间 |
| 序列时钟 | `elapsed × 1.5` | 参数时长要除以 1.5 才是实际秒数 |

例如首环 `Duration=1.15` 对应约 0.77 秒，不能直接写成 1.15 秒。判断“起步慢”要看首次可见、第一次穿过人物的时间，而不只是总播放时长。

不要放大整个父节点来同时修改环大小和路程。几何尺寸、位移范围、线宽、淡入和发射间隔分别调，才能知道反馈对应哪个参数。

重复触发使用独立序列：`Pulse()` 追加一个起始时间，旧序列继续播放。不要每次重置唯一进度，否则快速抽牌会反复打断动画。叠加后仍要观察亮度、声音和遮挡是否过量。

## 8. 原生消耗复用与对象池教训

用户要求原版消耗风格时，优先调查原版效果的创建、播放、资源和回收路径。本轮自制消散与原生风格差异明显，最终直接让抽牌堆图标承接原生效果，无需逐张展示被移除卡牌。

版本差异必须查实际调用点：正式版 v0.107.1 的 `NExhaustVfx` 与测试版 v0.111.0 的 `NCardExhaustVfx` 生命周期不同；测试版仅 `Create` 不会完成播放，还需要 `PlayAnimation()`。粒子、灰化材质、声音也应分别确认，不能用“节点创建成功”判断效果出现。

### 临时载体归还对象池前，必须恢复干净

本轮最重要的缺陷是：原生效果需要 `NCard`，于是借用卡牌节点、隐藏卡面并添加抽牌堆 `TextureRect`。动画完成后节点经 `QueueFreeSafely` 回到共享对象池，临时图标却留下了。下一张抽到手里的卡复用该节点，卡面就附带抽牌堆 icon。

修复方法：

1. 仅给借用的载体标记状态，保存直接子节点可见性、材质继承、自身可见性与鼠标过滤状态。
2. 在 `NCard.OnFreedToPool` 前移除临时图标并恢复状态，不等待外层塔动画结束。
3. 清理幂等，完成后清除标记，正常结束和中断回收走同一入口。
4. 不对所有普通卡牌做无差别子节点清理。

**手牌数量一致不代表显示正确。** 缺陷复现时模型与可见节点都是 4 个，但其中一张带有残留纹理。`karen_check_hand` 因此增加了 `unexpectedPileIcons` 检查。它专门覆盖已知 draw_pile 纹理残留，不能替代所有视觉检查。

本轮先部署检查复现失败，再部署修复执行同一路径，最后查看连续抽牌帧。详见 [对象池缺陷、回归与最终录像记录](testing/void-exhaust-carrier-pool-2026-09-29.md)。

## 9. Hover、声音与退出清理

Hover 是独立生命周期，要覆盖进入、退出、切换目标、卡牌取消和战斗结束。卡牌 hover 与目标生物 hover 不是同一个事件；直接调用回调只证明回调效果，不能声称真实鼠标命中链路也已测试。

跟随 Boss 的效果依据真实 hitbox 和全局变换定位；涉及材质采样的偏移还要考虑纹理尺寸。停止时先杀掉仍在淡入的 Tween，淡出回调捕获要清理的具体节点，避免旧回调误删新效果；父节点释放前妥善结束独立遮罩。

游戏流程等待应考虑游戏速度及原生命令约定，不能一律用固定 `Task.Delay`；媒体播放与表现时钟则按各自语义处理。声音也有归属：原生效果已经播放音效时不要重复叠加，连续触发时检查节拍和响度。

## 10. 验证与展示分开安排

| 层次 | 检查什么 | 容易漏掉的问题 |
| --- | --- | --- |
| 规则状态 | 牌堆数量、模式、卡牌归属 | 视觉补牌意外改变模型 |
| 可见节点 | 手牌模型与节点对应、临时子节点 | 数量一致但有残留图标 |
| 动画过程 | 起点、中途、终点及连续帧 | 中途跳位、第一次触发太慢 |
| 生命周期 | 连续触发、取消、回收后再抽牌 | 对象池污染、旧 Tween 回调 |
| 组合 | 能力单独、不同开启顺序、批量补牌 | 重复出生、数字状态错误 |
| 环境 | 版本、日志、声音与相关联机场景 | 用单版录像推断全部兼容 |

涉及移牌时通过 MCP 保存并查看前后截图，动画结束执行只读命令 `karen_check_hand`，同时核对过程录像。组合测试需要关注空堆、单张、多张、连续抽取及模式切换顺序。

四个能力有含基础状态在内的 16 种子集，但子集覆盖仍不等于开启顺序和所有边界都覆盖。面向用户可以只选有趣组合，测试记录必须如实标明未测部分。

按仓库要求，运行行为改动需关注正式版与测试版的实际单人验证及适用的多人矩阵。用户明确缩小本轮测试范围时，记录执行范围与未测原因；单版精选展示不能当成双版本或多人兼容结论。具体环境与套件见 [开发环境](dev-environments.md)、[批量测试矩阵](testing/mcp-batch-matrix.md)。

日志结论要分阶段。如启动已有错误、战斗段无新错误，应分别记录，不能合并成“日志无错误”。

## 11. 制作用户能判断的实机录像

游戏操作使用 [KarenSTS2MCP](external/KarenSTS2MCP.md)，不使用 Computer Use。先确认对应日志中服务已加载：独立正式版端口 `15627`，测试版 `15628`；Steam 环境 `15527` 不应混用。

1. 部署并确认运行的是本次构建，必要时记录 DLL 哈希。准备干净、可重复的战斗和卡牌状态。
2. 先调通操作和断言，再正式录制，避免成片包含准备卡组、切设置、长时间等待等过程。
3. 开启游戏进程声音录制，并确认游戏未静音；结束后恢复原设置。按实际片段长度配置录制时限，避免截断收尾。
4. 每段至少展示触发、主要运动和结果；常驻特效留出观察时间，取牌还要展示进入手牌后的状态。
5. 右上角标记能力组合与当前阶段，避开 HUD。按实际素材时长制作字幕和章节，检查最长组合名称。
6. 保持游戏原速；不要为掩盖节奏问题加速成片。若调音量，先检查峰值，不套用固定增益。
7. 检查录制完成状态、帧率和时长，查看关键连续帧；用媒体工具检查音轨并确认实际有声，只有 `audio:true` 元数据不够。
8. 最后回看编码后的成片，确认字幕、声音、清晰度、抽牌残留和结尾完整。

精选展示可采用“四个单独能力 + 空虚与再生产 + 燃烧与过去未来 + 四能力全开”。本轮最新精选约 88 秒，作为节奏参考，不是固定模板。

录制 MP4 与游戏内播放的 OGV 是两件事；后者的资源接入约定见 [Godot 视频特效接入经验](14.Godot视频特效接入经验.md)。

## 12. 留存、清理与交接

保留最终视频、必要截图、录制脚本、操作与断言结果、版本和提交信息。删除工作树前，先把需要交付的材料复制到主仓库留存目录并核对；不要让文档唯一证据指向即将删除的路径。

当前本机最新精选文件为 `artifacts/vfx-review/promise-highlights-2026-09-29/promise-highlights.mp4`；证据归档为 `artifacts/vfx-archive/void-activation-design-evidence`。这些本地产物不保证随仓库克隆提供。旧完整录像虽然包含 icon 修复，但环参数早于最新调整，不能冒充最新成片。

清理只针对已确认的任务中间产物，保留其他任务文件。归档后的旧 JSON 可能仍记录已删除的原始录制路径，应区分历史元数据和现存文件。删除失败或被拦截时明确记录剩余目录，不宣称全部清理完成。
