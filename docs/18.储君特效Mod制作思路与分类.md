> 整理日期：2026-10-12。用途：在重新设计 Karen 卡牌特效之前，按卡牌类型、规则效果、视觉结构和触发时点拆解《万象辉星 / Regent FX Omnistar》。
>
> 证据口径：源码与资源静态分析；已查看原始透明 PNG 动画和场景结构，未在游戏中逐张播放该 Mod。本文中的代码行为是源码事实，制作方法的归纳是分析结论，Karen 的取舍是建议。

### 1.1 覆盖的是 25 张牌的不同表现层

源码注册了 21 个 CardFX 和 4 个 PowerFX。对应原版卡牌实际类型为：

| 实际 CardType | 数量 | 入口 |
| --- | ---: | --- |
| Attack 攻击 | 16 | 单体、群体、多段、随机、成长攻击 |
| Skill 技能 | 5 | Alignment、BigBang、Glow、ParticleWall、Resonance |
| Power 能力 | 4 | BlackHole、Genesis、PillarOfCreation、SpectrumShift；通过关联 PowerFX 接入 |

这不是储君全部卡牌目录，也不是“25 张卡各自拥有独立全屏动画”。星环、持牌星星、命中粒子、常驻黑洞、音效、曝光等是复用层；一张牌可以组合多个层，一组帧也可能只服务其中一个阶段。

### 1.2 资源规模

| 资源 | 数量 | 解读 |
| --- | ---: | --- |
| .tscn | 45 | 主场景、子场景、辅助场景合计 |
| .gdshader | 16 | 发光、扭曲、黑洞等 |
| .tres | 16 | 材质等文本资源 |
| PNG | 1210 | frames 目录 1128 张，其他图片 82 张 |
| frames 分组 | 21 | 包含 super_massive 等多动画组 |
| frames PNG 文件总大小 | 约 71.53 MiB | 压缩文件大小，不是显存占用 |
| 音频发布资源 | 1 bank + 1 GUID 表 | 另有 FMOD 工程与源音频 |

场景文本中出现 24 个 AnimatedSprite2D、22 个 GPUParticles2D、13 个 Sprite2D、4 个 BackBufferCopy。它们是全资源统计，不能当作一次出牌的节点数。

**核心结论：画面复杂度大量预先做进透明 PNG 序列，再由实时星星、GPU 粒子、Shader、镜头和音频补足交互。** “多加粒子”只是其中一个手段；主体轮廓、速度变化和亮度节拍往往已经烘焙在帧图里。

没有发现 .aep、.blend、.psd、.hip 或 .c4d 等作者制作源文件。可以确认使用序列帧，不能确认是用 AE、Blender、Houdini 或哪种工具制作。

## 2. 先区分三种分类维度

设计时要同时写出这三列，不能用“它是能力牌”直接决定播放什么：

| 维度 | 回答的问题 | 例子 |
| --- | --- | --- |
| 卡牌类型 | 原版怎样管理打出与牌堆去向？ | Attack / Skill / Power |
| 规则效果类型 | 实际发生什么、发生几次、对谁发生？ | 群体两击、随机 X 击、获得格挡、每回合生成卡 |
| 表现类型 | 玩家通过什么运动理解这件事？ | 投射、坠落、爆发、内收、上涌、常驻物激活 |

Resonance 是技能，却同时改变自己和全部敌人的力量。Supermassive 是攻击，却在打出之前已有常驻成长物。SpectrumShift 是能力，却在本 Mod 中主要加强初次施放，没有给每次生成无色牌添加一套专属运输演出。

因此，**卡牌类型负责流程，效果类型负责反馈位置与次数，表现类型负责美术动作**。

## 3. 按卡牌类型逐张分析

以下“规则摘要”只用于特效分类，不代替完整卡牌文本。数值升级和费用变化应回查对应 v0.107.1 反编译文件。

#### 攻击牌的共通思路

1. **先给方向，再给冲击。** 起点高于角色、目标使用 VfxSpawnPosition，玩家能够读出能量从哪里来、打向哪里。
2. **主动画负责形状，微小随机负责变化。** 随机上下翻转、起点抖动、尺寸与颜色变化只改变视觉，不重新选择战斗目标。
3. **重度随用途分级。** Strike 的 0.05 秒命中、Shining 的短斩击与 Comet 的 0.6 秒起势不是同一个预算。
4. **多段不重播整场大招。** AstralPulse 的主体在 Execute 前一次，Radiate 的短脉冲每击一次，SevenStars 的准备星每击消耗一个。
5. **结算后的附加规则不必拥有第二套大演出。** 抽牌、得星、锻造、虚弱/易伤继续使用原生命令与 Power 的反馈。

### 3.2 技能牌：5 张

| 卡牌 | 规则摘要 | Mod 表现 | 制作思路与限制 |
| --- | --- | --- | --- |
| [Alignment][fx-alignment] | 消耗 3 星，获得能量 | 三颗星在头顶横向连接，大小递减；角色位置播放 alignment 序列与声音，归还准备星 | 把资源转换表现为“聚集 → 点亮”；原 GainEnergy 给真正回能反馈 |
| [Glow][fx-glow] | 得星、立即抽牌并设置下回合抽牌 | 不借星；角色位置短序列，0.1 秒后抬曝光，再恢复 | 轻量收益使用一次上升/发光，不逐个收益重复施放；下回合抽牌未另设专属循环 |
| [BigBang][fx-bigbang] | 抽牌、得星、回能、锻造；消耗 | 无持牌星；大爆发序列；0.25 秒后音效与曝光，0.3 秒后强震屏 | 多项收益共用一个“创生”母题；实际各项收益仍依序原命令执行 |
| [ParticleWall][fx-wall] | 获得格挡，通常回到手牌 | 两颗星在前方上下错开；角色前方粒子墙序列，镜像朝向，缩放 0.7 | 格挡的空间关系放在角色前方；墙是短演出，不是新建一套永久格挡规则 |
| [Resonance][fx-resonance] | 自己加力量、全部敌人减力量 | Custom 借三颗轨道星，变金并扩轨至 1.5；后层序列、曝光、星点爆闪；取消时复原颜色/轨道 | 能量共鸣可用已有对象变状态；“技能”也可产生持续数值，无需常驻大光环 |

这里多用 OnPlay 的 **void Harmony Prefix 启动异步演出**，原方法继续运行。它们不都保证“画面峰值到达后才结算”。这种写法能减少改动，但不能直接当作 Karen 结算同步方案。

技能分类最重要的是**分清这次得到什么，与未来什么时候继续得到什么**。Glow 的当次收益、下回合收益，以及 BigBang 的多项收益，被一个短演出概括；没有为每一种规则变化都画独立实体。

### 3.3 能力牌：4 张

| 卡牌 / Power | 实际后续行为 | Mod 的生命周期 | 最值得学的部分 |
| --- | --- | --- | --- |
| [BlackHole][fx-blackhole] | 获得星星后、消费星星的出牌完成后，对全部敌人造成伤害 | Power 施加前创建后层黑洞；Amount 改尺寸；伤害方法补丁触发 Burst；Power 移除释放 | 同一常驻物反复激活，比每次重新出生更有积累感 |
| [PillarOfCreation][fx-pillar] | 本人生成战斗卡牌后获得格挡 | 施加时柱体落下；Amount 改尺寸；生成事件激活 Active 层；移除释放 | 默认层负责存在，短亮层负责触发，循环动画不重启 |
| [Genesis][fx-genesis] | 每回合能量重置后获得星星 | 施加 Power 前播放大型序列、两段声效、曝光、扭曲；约 4 秒清理 | 本 Mod 强调初次施放；并没有在这里为每次得星建立 Genesis 专属常驻节点 |
| [SpectrumShift][fx-spectrum] | 每回合抽牌前生成无色牌加入手牌 | 施加 Power 前一次光谱序列与音效，约 3 秒清理 | “持续效果”并不必然需要“持续亮物”；后续生成牌依旧使用原版流程 |

**常驻能力与一次性能力演出是两套结构。** BlackHole、Pillar 是“建立 → 等待 → 激活 → 等待 → 删除”；Genesis、SpectrumShift 是“施放 → 删除”，后续只保留模型能力和原生反馈。

PowerFX 在 BeforeApplied 之前启动，也不代表能力一定已成功获得。Karen 如果要显示“已获得/已存入”的确认信号，应该以真实模型变化和命令结果为准。

## 4. 按卡牌效果类型总结制作方法

### 4.1 单体直接伤害

- **空间语法：** 角色准备点 → 目标身体/命中点。
- **组成：** 一条方向明确的主序列 + 目标短冲击 + 声音 + 轻震屏。
- **参考：** SolarStrike、ShiningStrike、CrescentSpear、StrikeRegent。
- **变体控制：** 起点少量抖动、翻转纹理、旋转适配距离；保持终点准确。
- **关键约束：** 不用视觉随机重新抽目标；目标死亡或节点不存在时只跳过画面，规则仍按原命令执行。

### 4.2 重击与复合攻击

- **空间语法：** 高处聚集 → 大体积释放 → 集中冲击。
- **组成：** 准备星、较长主序列、局部闪白/曝光、强度较大的震屏。
- **参考：** Comet、WroughtInWar、FallingStar。
- **制作结论：** 高强度来自密度集中与峰值节拍，不是整个生命周期都最亮。
- **附带减益/锻造：** 给主命中让出视线，由实际 Power/Forge 命令接续，不在攻击起势时提前显示完成。

### 4.3 群体伤害

- **空间语法：** 敌方区域级主体 + 每个实际目标的小命中。
- **参考：** AstralPulse、DyingStar。
- **关键分工：** 大主体一次，目标冲击可多次；群体中心用于构图，实际敌人列表用于结算。
- **Karen 转译：** 多人共同演出也应一次共享起势，各玩家分别确认，避免按人数重复整个画面。

### 4.4 固定多段与可变多段

| 子类 | 参考 | 可数对象 | 每次触发的视觉单位 |
| --- | --- | --- | --- |
| 固定七击 | SevenStars | 七颗准备星 | 一颗退出 + 各目标 Blade |
| 单体可变击数 | LunarBlast | 由 CalculatedHits 生成的准备星，最多显示 20 | 一颗星的发射位置 + 激光 + 月光 |
| 群体可变击数 | Radiate | 不强制为每击建立常驻实体 | 一次短环脉冲 + 能量粒子 |
| X 星随机多击 | Stardust | 借全部可显示星星 | 向本击实际目标飞一颗星 |

**固定、可变、随机三者不能共用“按预览数量跑完就算结算”的假循环。** 次数由规则决定；视觉可以限流、合并声音、压缩尾迹，但不能改变实际击数。

### 4.5 格挡与防御

- ParticleWall 的重点是角色前方屏障位置；Pillar 的重点是生成牌事件令已有柱体亮一下。
- 原版 GainBlock 的数字与图标已经能说明获得量，不再另造同样的数值飘字。
- “获得格挡”和“格挡在之后被打掉”是不同事件。Mod 的粒子墙是施放演出，没有据其存续时间维护实际格挡。
- 防御特效可遮挡攻击通路的想象空间，但应保持人物、生命条和卡牌可读。

### 4.6 力量等增益 / 减益

- Resonance 用轨道扩张、暖色、后层爆发说明强化；敌人降力量继续由 Power 反馈。
- 暂时增益、永久数值增益、常驻触发能力不等同。永久力量无需整场保留三根光束。
- 对 Karen 的力量牌应把成功确认接在实际 StrengthPower 变化后，区别“准备提升”和“已经提升”。
- 临时力量消退可以使用图标及数值反馈，没必要每回合重新播放完整获得动画。

### 4.7 回能、得星、抽牌等资源收益

- Alignment、Glow、BigBang 的主动画强调收益来源，PlayerCmd/CardPileCmd 完成实际反馈。
- 星环把 Stars 可视化成可计数对象，准备星把即将花费的资源临时组织成卡牌构图。
- 原版模型 Stars 变化驱动环中星数，视觉不维护另一套资源账本。
- 如果有多项收益，只在总演出起势一次；各收益的落点由其原生命令依序确认。

### 4.8 卡牌生成与成长积累

- Pillar 监听本人生成卡牌，激活同一个柱体；Supermassive 从生成历史计算成长。
- Supermassive 的球大小采用平方根增长并限幅，而不是牌数线性放大至遮满屏幕。
- 成长附加层不打断球的循环主体，使“已经在场的物体更强”容易理解。
- 卡牌进入手牌、约定牌堆、抽牌堆的目的地不同，生成动画应使用真实落点及真实 CardModel 身份。
- SpectrumShift 展示了另一种合理取舍：加强初次施放，后续生成交给原版。

### 4.9 卡牌返回、变牌、奖励：本 Mod 的覆盖边界

ShiningStrike 回抽牌堆顶、MakeItSo 回手、ParticleWall 回手都有实际规则；本 Mod 没有为它们统一建立“实体卡牌运输框架”。它们的专属演出主要仍是攻击或防御。

这套源码没有可直接照搬到 Karen 的“什锦变晚餐”“每卡一星的约定牌堆”“药水栏取得药水”或“多人战后奖励派发”模块。能借鉴的是分阶段、成功确认、对象身份与退场方法，具体接线要依靠 Karen 与原版已有命令。

### 5.2 实时星星：负责准备、计数和连续性

[StarRingController][src-ring] 在角色附近维护轨道星：

- 基础半径 120，转速 30 度/秒，垂直偏移 -180，最多显示 20 颗。
- 椭圆纵深、前后 ZIndex、小范围尺度变化制造环绕体积感。
- 新星从统一位置生成并长大，已有星重新均分相位时尽量减少移动。
- 每帧跟随角色位置与缩放；这比把一圈星画死在视频里更能适应角色变化。

[StarEffectController][src-effect] 负责临时借出、重排、抖动、Pop 和取消恢复。CardFX 的 HoldingMode 把行为分成：

| 模式 | 功能 | 参考 |
| --- | --- | --- |
| BorrowDefault | 按配置数量借轨道星，排成卡牌准备队形 | SevenStars、FallingStar |
| BorrowAll | 借全部可显示星 | Stardust |
| Custom | 卡牌自行组织 | LunarBlast、Resonance |
| None | 不建立准备星 | SolarStrike、BigBang、Radiate |

星星自身有亮核、Glow、移动尾迹、旋转与呼吸；连线由绘制完成，颜色材质为实例独立副本。准备阶段已经产生可辨识画面，因此实际打出不必从零重新介绍主题。

要注意：ReturnAllStars 会销毁临时星并按真实 Stars 重建星环，不是所有情况都把同一节点连续送回。Karen 的约定牌堆要求每个 CardModel 对应具体星节点，应该沿用项目已有身份与交接机制，不能直接复制这个重建方式。

### 5.3 GPU 粒子：负责数量感、尾迹和短脉冲

使用 GPUParticles2D 的场景包括星尾、能量、脉冲等。粒子通过数量、寿命、爆发性、速度、尺度曲线、透明度渐变实现：

- **起势：** 向中心内收或从脚底上涌。
- **移动：** 拖尾只在运动时开启，静止时退出。
- **命中：** 一次 explosive 爆发，短寿命高对比。
- **余韵：** 扩散、减速、变暗，比主体稍晚消失。

Radiate 的扭曲环和颜色环各只有 **amount=1**，却通过纹理、Shader、尺度曲线形成明显的环形能量。由此可见“看起来粒子多”和“GPU 粒子数量大”不是同一件事；有些丰富结构来自贴图内部。

### 5.4 Shader：负责活性和空间扰动

| 类别 | 参考 | 工作方式 | 适合什么 |
| --- | --- | --- | --- |
| 发光增强 | base.gdshader、材质参数 | 依据亮度添加 Glow，部分实现可选模糊 | 亮核、短束、星体 |
| 黑洞核心 | [blackhole_core.gdshader][shader-hole] | 径向脉动、UV 旋涡、纹理透明度、边缘亮环、多频暗部闪烁 | 需要长时间“活着”的常驻物 |
| 屏幕扭曲 | [radiate_ring_distortion.gdshader][shader-radiate] | SCREEN_UV、屏幕纹理、环形遮罩、噪声位移、切向旋流、RGB 分离 | 很短的冲击或爆发 |
| 粒子生命周期调制 | radiate 脉冲场景 | 用粒子归一化寿命驱动 sin(tπ) 强度包络 | 出现与消失都平滑的短脉冲 |

BackBufferCopy 为屏幕取样提供背景。扭曲应该围绕明确事件发生，而不是为了“高级”长期覆盖人物、卡牌和 UI。

Radiate 会 Duplicate ShaderMaterial 再设置随机参数，避免同资源实例互相污染。Karen 的颜色、强度、进度等如果按单次演出变化，也需要实例隔离。

### 5.5 原版节点与场景复用：负责游戏风格统一

SolarStrike、Radiate、Stardust 等复用原版储君能量场景和 starry impact。它们与自制序列混合，令攻击声音、能量颜色、受击质感仍能融入游戏。

[StarryImpactPatch][patch-impact] 只对登记过的自定义创建节点做特殊调整：移除烟与扭曲、缩小粒子材质后重播。不能把它理解为无条件修改所有原版命中特效。

对 Karen 的原则是：原版烟、PowerUp 亮束和星点提供基础质感，现有舞台灯与星运输提供角色主题，新的运动编排提供卡牌辨识度。

### 5.6 曝光、震屏与声音：负责峰值节拍

画面强度通常分为三个时刻：

1. 起势低亮度，让方向和对象可读。
2. 峰值给短曝光/冲击声/震屏。
3. 主体尾迹继续退场，曝光先恢复正常。

这是分析得出的编排共性，不是每张牌都严格使用相同时间线。

[WorldEnvironmentUtil][src-world] 的 TweenExposure 实际公式为：

~~~text
finalExposure = (exposure - 1) * Setting.ExposureThreshold + exposure
~~~

例如 threshold=1、调用 exposure=1.3 时，最终目标是 1.6。不能把配置值直接当作游戏最终曝光。独立 Tween 也没有统一仲裁所有并发演出；直接照搬会增加多卡效果互相恢复曝光的风险。

音频包含 FMOD 工程、源音频、发布 bank 与 GUID 表。持牌、释放、命中、成长使用不同事件；Supermassive 会用尺寸参数改变创建/成长/发射事件。C# 通过轻量 FmodServer 桥接装载，不以 RitsuLib 是否安装作为唯一播放前提。

对六张 Karen 收益牌的初稿建议使用已有增益、卡牌生成、药水取得反馈，并为主题层加短音色；没有必要照搬攻击类的强震屏、全屏闪白或长轰鸣。

## 6. 如何把场景放到正确的位置

[CardVfxUtil][src-cardutil] 和 [VFXUtil][src-util] 提供单体、区域和前后层挂载：

- 角色准备点来自 GlobalPosition + 卡牌偏移。
- 目标命中点通常来自 NCreature.VfxSpawnPosition。
- 群体主体可以放在敌方区域位置。
- PlaySimple 使用战斗前层，PlaySimpleBack 使用战斗后层。
- 横向定向素材通过 StartPos 与终点适配真实距离。

FitVFX 的几何思想：

~~~text
模板方向 = sceneEnd - sceneStart
真实方向 = targetEnd - targetStart
缩放 = |真实方向| / |模板方向|
旋转 = angle(真实方向) - angle(模板方向)
再设置根位置，使模板的终点落到真实终点
~~~

它适合“已经画好的一条攻击”。若素材中的圆形、宽度也随等比缩放改变，远距离时可能过粗；收益运输则更适合实时路径、固定粒子宽度和动态目的地。

部分卡有镜像处理，部分直接使用固定偏移；环控制器也直接读 Visuals.Scale.X。阅读这些实现不能得出“所有角色缩放、镜像、多人位置都已稳健适配”。Karen 应从 Hitbox、GlobalTransform 与既有坐标服务出发，避免散落固定屏幕坐标。

## 7. 触发时点和控制结构

### 7.1 一次出牌的概念流程

~~~text
开始持牌
  → 准备星借出 / 重排 / 颜色变化
取消持牌
  → 停止抖动、声音与尾迹，恢复准备状态

真正出牌
  → CardFX / AttackCommand 的 BeforeExecute（整体起势）
  → 每击 BeforeDamage（定向或群体短演出）
  → CreatureCmd.Damage（真实规则与受击反馈）
  → 出牌结束 / finally（清理或恢复准备星）
~~~

技能牌的 OnPlay Prefix 与能力牌的 BeforeApplied Patch 是另外的入口，并不都按上述攻击链路等待。

### 7.2 不同事件应该挂在哪一层

| 事件 | 储君源码入口 | 应负责的画面 |
| --- | --- | --- |
| 开始拖牌 | CardPlayTimingPatch / StartCardPlay | 预备队形、轻微呼吸 |
| 取消拖牌 | CancelPlayCard | 全部准备状态恢复 |
| 攻击整体开始 | CardAnimPatch / OnBeforeExecute | 一次起势和主场景 |
| 每次实际伤害 | BeforeDamage / DamageTargetPatch | 本击与实际目标相关的短表现 |
| 出牌结束 | OnPlayWrapper 的 finally | 准备对象恢复和上下文标记清理 |
| 施加能力 | PowerTimingPatch / BeforeApplied | 初次建立或施放 |
| 能力层数变更 | SetAmount | 尺寸与强度参数 |
| 能力触发 | 具体 Power 方法补丁 | 常驻物激活 |
| 能力移除 | AfterRemoved | 常驻物释放 |

### 7.3 随机目标要在结算附近取得

Stardust 使用 [DamageTargetPatch][patch-target] 在 CreatureCmd.Damage 附近获取实际 targets；源码兼容不同参数数量的 Damage 重载，并有递归深度保护。

如果只在 AttackCommand 的早期读取 _singleTarget，随机攻击可能还没有这个目标。对于 Karen 的多人奖励，也应该以本次真正得到标记的 Player 为准，不能只用预览页面固定的两个队友。

### 7.4 注册、预加载与设置

[Entry][src-entry] 负责 Harmony、Godot ScriptManagerBridge、音频与设置；[CardFX][src-cardfx] 和 PowerFX 使用特性及反射建立映射。

ModSceneCache 保存 PackedScene，扫描全部声明 AssetPaths 与公共场景，目的是避免部分资源只随角色预加载后被卸载。它是资源缓存，**不是特效节点对象池**。

CardFX 配置集中保存准备模式、星数、队形、SFX、场景、清理延迟、曝光、是否抑制默认武器等，单卡通过覆写提供动作。其接口思想值得借鉴：共享流程收口，单卡只描述差异。

实际 Karen 六张牌更适合先共用“施放—结算确认—运输—退场”流程，再分别配置烟、粒子、灯和落点，不需要为了这次设计直接引入完整反射 FX 框架。

## 8. 常驻物：Supermassive 与 Pillar 的完整案例

### 8.1 Supermassive 的三个状态

| 状态 | 触发 | 视觉动作 |
| --- | --- | --- |
| 等待 | 相关牌仍在有效牌堆 | 球体持续播放 ball，跟随角色并缓慢游走 |
| 成长 | 本人生成战斗卡牌的历史增加 | grow 叠加 0.4 秒，尺寸和声音参数更新；ball 不重启 |
| 释放 | 打出 Supermassive、取得实际目标 | 保存 GlobalTransform 后换父节点，0.15 秒加速飞行；爆炸 AnimationFinished 清理 |

球体存在检查覆盖手牌、抽牌、弃牌和打出牌堆，不把消耗堆作为仍持有依据。ContentsChanged 事件合并为 CallDeferred 更新，避免一次操作中反复同步。

_lifecycleVersion 阻止旧回调重建失效物体；退出时停止 Tween 并取消事件订阅。这比简单的“等三秒后 QueueFree”更适合后续仍会再次触发的对象。

**局限：** TryLaunch 启动视觉飞行后就返回，CardFX 的 OnBeforeDamage 返回 CompletedTask；没有等待球到达再伤害。它提供优秀的持有、成长、交接案例，但不是严格落点同步范本。

### 8.2 Pillar 的默认层与激活层

Pillar 由 Top、Spin、Main、Light 等层组成。Base 与 Active 分开，激活层同步默认动画当前帧，使短亮脉冲不显得像重新召唤柱体。

出现时从上方落入；触发时 Active 快速变亮再恢复；Amount 增加只改尺寸；Power 移除释放同一柱体。常驻柱与黑洞创建时取得位置，代码没有像星环一样每帧跟随角色，因此适配角色移动时还需额外设计。

Karen 已有约定之塔、库存星、火焰/空虚入口，应该强化这些真实状态物，不再为每张收益牌增加一个新的常驻舞台装置。

## 9. 值得学习与需要改进的边界

| 问题 | 源码事实 | Karen 的取舍 |
| --- | --- | --- |
| 视觉丰富度 | 序列帧、实时星、粒子、Shader、原版场景混合 | 用一层明确主体加两三层辅助，先确定运动再增加密度 |
| 可变次数 | 七击、CalculatedHits、X 星有不同准备与逐击策略 | 层数影响派发数量，不重复整个母演出 |
| 收益确认 | 多个 Prefix 在规则之前启动视觉 | 成功亮闪、入栏、入堆以实际结果为准 |
| 命中同步 | Stardust 伤害前等 0.1 秒，飞行约 0.35 秒；Supermassive 不等待落点 | 重要运输必须共享明确交接点，视觉取消不取消规则 |
| 对象连续性 | 某些借星最终重建；Supermassive 保存 GlobalTransform 换父节点 | 约定星和原生药水运输保持同一对象/明确交接，避免双实体 |
| 材质隔离 | Star、Radiate、黑洞等 Duplicate 材质 | 单次参数变化使用实例材质 |
| 全局状态 | 当前卡、若干标记与控制器单例；部分 AsyncLocal | 不把视觉上下文作为联机规则依据；按 Owner 和事件实例区分 |
| 全局曝光 / 层级 | 曝光多个 Tween；ZIndexPatch 修改所有 Creature 与容器 | 六张收益牌默认使用局部光；遵循已有战斗前后层 |
| 生命周期 | Power 移除释放；Supermassive 有订阅与版本清理 | 每种演出列出结束、取消、退出战斗、对象消失的退场路径 |
| 性能 | 大量高分辨率帧，预加载场景 | 高频效果以小贴图和程序粒子为主，罕见高潮才考虑大序列 |
| 兼容 | Damage 重载反射、FromCard 签名适配、Transpiler 兜底 | 继续使用 Karen 的双版 Compat，不复制游戏规则方法 |

### 9.1 纹理成本不能只看 PNG 大小

1128 张 frames 以 RGBA8、无 mipmap、全部驻留的简单假设估算，基础像素总量约 **2.53 GiB**。这不是实测显存，也不等于真实导入、压缩或缓存占用；统计包含场景未使用的保存帧。

AstralPulse 的 44 张 1920×1080 PNG 文件约 10.02 MiB，简单解码像素量约 348 MiB。文件压缩率高，不表示播放资源成本低。

因此给 Karen 制作大帧动画时，应记录实际引用帧数、纹理尺寸、导入格式、预加载范围和峰值同时实例数；先裁透明边缘、删除不用帧，再讨论降分辨率或图集。不能把 HTML 中 1000 个 Canvas 粒子当成游戏性能结论。

### 9.2 “画得多”之前先回答的六个问题

1. 谁发起：角色、实际卡、能力图标还是已在场的状态物？
2. 在哪里发生：身体、敌人、手牌、药水栏、约定入口还是队友标记？
3. 发生几次：一次施放、每击、每层、每回合还是每个玩家？
4. 哪个画面表示成功：局部闪亮、真实对象到达、图标增长还是节点激活？
5. 留下什么：能力图标、库存星、常驻物，还是全部视觉退场？
6. 取消时怎么办：规则照常执行，视觉恢复或直接清理？

回答这些以后再选择粒子、序列帧或 Shader，才能让资源服务规则。

## 10. 后续 Karen 设计应采用的制作流程

1. 阅读当前 worktree 的真实卡牌规则、玩家已选方向、现有实现和验收记录。
2. 分别画出“首次施放”和“后续触发”时间线；只对确有延迟触发的牌画第二条。
3. 用一个主运动区分卡牌：成瓶、上涌、暖辉、派牌、双流汇合、队伍脚灯。
4. 明确实际结算节点、成功条件和真实目的地；不让演出再次执行命令。
5. 选择主体层、后层体积、前层细节；三者错开出现和退出。
6. 高层数共用起势与低亮背景，单个收益只派发一个短单位。
7. 保存本次实例的 Owner、CardModel/Player 身份、Tween/回调与清理路径。
8. HTML 用于看构图和节拍；Godot 实机用于校准遮挡、HDR、实际运输及性能。
9. 根据项目规范做改动相关的双版针对性验证；移牌保存 MCP 前后截图并执行 karen_check_hand。文档和预演阶段不宣称完成游戏测试。

逐张 Karen 对照与重设计另见 [六张卡牌特效对照与重设计](design/六张卡牌特效对照与重设计-2026-10-12.md)，避免把源码事实与新方案混在一起。
