## 性能审查与优化（2026-10-29）

用户原话：你看看代码，分析下这个占用性能大吗？怎么优化下？

计划：先在隔离游戏中测量最小化/暂停/展开播放状态的实际回调和刷新次数、UI 回调分配及开销，再据此最小化修改；检查选曲加载及本地目录的大文件风险，保留既有外观与交互。只执行与优化直接相关的定向验证。

### 性能结果

当前播放器 UI 属于轻量开销。正式版基线预热后，60000 次手动回调中位数 7.3581 ms，分配 3040152 字节；优化后正式版为 0.8216 ms、测试版为 0.7865 ms，两版该压测分配均为 0。此为 UI 方法微基准，不含引擎调度、音频解码及整体游戏帧率。

实际运行约 2 秒的统计：

| 状态 | 优化前回调 / 时钟 / 布局 | 优化后回调 / 时钟 / 布局 |
| --- | --- | --- |
| 最小化待播放 | 122 / 12 / 12 | 0 / 0 / 0 |
| 最小化播放中（提示收起后） | 121 / 12 / 12 | 0 / 0 / 0 |
| 展开播放中 | 122 / 12 / 12 | 正式版 121 / 12 / 0；测试版 122 / 12 / 0 |
| 展开暂停中 | 123 / 12 / 12 | 0 / 0 / 0 |
| 配置关闭 | 122 / 0 / 0 | 0 / 0 / 0 |

- 最小化、暂停、隐藏时停止周期 UI 回调；歌名提示及延迟重载临时唤醒，展开播放继续刷新进度。
- 布局改为展开、拖动、提示和视口尺寸变化时更新，移除时钟轮询中的重复布局。
- 首次打开曲库前曲目按钮从 20 个降为 0，打开时建立并复用。
- 暂停拖动进度时立即更新显示，并保留目标位置至恢复播放，避免依赖音频线程暂停时的旧位置。

内置音频运行时按选曲加载，代码只持有当前播放流，持续解码交给引擎。当前 20 首的 31.56 MiB 是磁盘曲库大小。可选本地目录仍采用一次性文件扫描与所选文件整文件异步读取；大型 WAV 或海量本地文件是后续更值得关注的内存/加载场景，本次保留既有格式与加载机制。
