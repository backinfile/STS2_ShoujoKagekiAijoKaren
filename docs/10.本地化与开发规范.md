# 本地化与开发规范

> 主题：文本、本地化、资源命名与通用开发约定  
> 适用范围：描述文本、关键字、资源命名、通用实现习惯  
> 阅读建议：新增内容前快速过一遍，能减少返工

---

## 本地化结构

当前项目文本并不只存在于“卡牌描述”里，还分散在这些位置：

- 卡牌描述文本
- `card_keywords` 关键字提示
- HoverTip 标题与描述
- 牌堆 / 模式 / 系统说明文本
- 视图和界面用 LocString

从 `CardHoverTipsPatch` 和 `CardKeywordInlinePatch` 可以确认：

- 关键字系统已经深度参与卡牌展示
- 一些提示不是写死在卡牌类里，而是通过标签和本地化表动态生成

## 文本格式

当前项目常见的动态文本写法包括：

- `{Damage:diff()}`
- `{Block:diff()}`
- `{Cards:diff()}`
- `{Energy:energyIcons()}`

这些写法要求：

- 对应 `DynamicVar` 必须真的存在
- 升级差值要能被正确计算
- 文本、数值、升级逻辑三者必须一致

## DynamicVar 文本约定

当前文档和代码里已经固定使用：

- `DynamicVar（动态变量）`

常见变量类型：

- `DamageVar`
- `BlockVar`
- `CardsVar`
- `PowerVar<T>`
- `EnergyVar`
- `DisableRelicVar`

如果卡牌描述里用了动态变量，但 `CanonicalVars` 没配完整，通常会直接导致：

- 文本显示不对
- 差值显示异常
- 视图补丁取不到对应数值

## HoverTip 与关键字约定

`CardHoverTipsPatch` 的现状说明了一条重要规范：

- 不要只把一个机制写进卡牌描述
- 还要考虑它是否需要成为统一关键字

当前已接线的 Karen 关键字至少包括：

- Shine（闪耀）
- PromisePile（约定牌堆）
- TmpStrength
- DisableRelic（禁用遗物）
- TokenCard

如果你新增一个系统概念，建议同时判断是否需要：

1. 新标签
2. 新 HoverTip
3. 新 `card_keywords` 文本

## 常用术语写法

正文中建议统一使用以下写法：

- Shine（闪耀）
- PromisePile（约定牌堆）
- GlobalMove（全局移牌）
- ExtraReplay（额外重播）
- DisableRelic（禁用遗物）
- DynamicVar（动态变量）
- Power（能力）
- Patch（补丁）
- Hook（钩子）

建议正文保持“英文标识 + 中文说明”的写法，不要在不同文档里来回换叫法。

## 开发实现约定

从当前代码结构看，建议遵循这些习惯：

- 新卡默认优先使用 `KarenBaseCardModel`
- 需要打牌条件控制时，再考虑 `KarenDisableRelicBaseCardModel`
- 系统扩展优先复用已有命令类和补丁入口
- 涉及联机选择时必须沿用 `PlayerChoiceContext`
- 描述里提到的系统概念，尽量让标签、文本、HoverTip 一起跟上

## 资源命名与目录映射

当前项目结构倾向于让资源和代码目录一一对应。

建议保持这些映射关系稳定：

- 卡牌类名 ↔ 卡牌资源名
- 角色 ID ↔ 角色颜色 / 能量颜色名
- 系统名 ↔ 关键字 / 标签 / 本地化条目

例如：

- `Karen.energyColorName = "karen"`
- `KarenCardPool.Title => "karen"`

这类命名稳定后，后面补资源和补本地化都会轻松很多。

## 药水规范写法

Karen 药水当前已经形成一套独立于 BaseLib `CustomPotionModel` 的项目内约定，后续新增药水建议统一按这套写。

### 基类与继承约定

- Karen 自定义药水统一继承 `KarenBasePotion`
- `KarenBasePotion` 直接继承原版 `PotionModel`
- 不再依赖 `CustomPotionModel` / `CustomPotionPoolModel`

这样做的目的：

- 减少 BaseLib 依赖面
- 保持药水逻辑和项目内其他自定义系统一样，主要通过原版模型 + Harmony Patch（补丁）接线
- 让图片路径、资源命名和池接入规则都由项目自己维护

### 图片资源约定

Karen 药水图片统一使用下面的命名规则：

- 主图：`res://images/potions/{PotionId.Entry.ToLowerInvariant()}.png`
- 轮廓图：`res://images/potions/{PotionId.Entry.ToLowerInvariant()}_outline.png`

对应代码位于：

- `src/Core/Models/Potions/KarenBasePotion.cs`
- `src/Core/Patches/KarenPotionVisualPatch.cs`

说明：

- `KarenBasePotion` 只负责暴露 `KarenImagePath` 和 `KarenOutlinePath`
- 真正把图片路径接到原版 `PotionModel` 上的是 `KarenPotionVisualPatch`
- Patch 拦截的是 `PotionModel.PackedImagePath` 和 `PotionModel.PackedOutlinePath`

这意味着：

- 新药水不需要各自再写一套图片加载逻辑
- 只要 `Id.Entry`、png 文件名和本地化键保持一致，UI 就能自动显示正确图片

### 药水池约定

Karen 角色应使用独立的 `KarenPotionPool`，不要继续直接复用原版角色药水池。

当前规范：

- 药水池类放在 `src/Core/Models/PotionPools/`
- 继承原版 `PotionPoolModel`
- 在 `GenerateAllPotions()` 中显式返回所有 Karen 药水
- 在 `CharacterModel` 中通过 `PotionPool => ModelDb.PotionPool<KarenPotionPool>()` 接入

这样做的好处是：

- Karen 药水列表可控
- 后续做专属药水、解锁、平衡调整时不会和原版池混在一起
- 文档、资源、角色接线是一一对应的

### 本地化约定

Karen 药水的本地化表统一放在：

- `ShoujoKagekiAijoKaren/localization/zhs/potions.json`
- `ShoujoKagekiAijoKaren/localization/eng/potions.json`

每个药水至少维护：

- `{POTION_ID}.title`
- `{POTION_ID}.description`

如果药水包含选择界面或额外提示，再补：

- `{POTION_ID}.selectionScreenPrompt`

当前 `KarenShinePotion` 就采用了这套结构。

### 实现效果时的建议写法

药水效果层建议遵循和卡牌类似的原则：

- 优先复用原版命令类，如 `CardPileCmd`、`CardSelectCmd`、`CardCmd`
- 需要自定义标题或选择行为时，再接项目内扩展命令，如 `CardSelectCmdEx`
- 涉及战斗内生成卡时，优先用 `CardFactory.GetDistinctForCombat(...)`
- 涉及把战斗牌变成永久牌时，优先用 `CardModelEx.CloneSafeForDeck()`

尤其要注意区分两类“拿到牌”：

- 加入手牌：通常走 `CardPileCmd.AddGeneratedCardToCombat(...)`
- 加入牌组：通常走 `CardPileCmd.Add(..., PileType.Deck)`

如果要同时加入手牌和牌组，建议先生成战斗牌，再克隆一份安全的永久牌加入牌组。

### 表现层约定

`await CardPileCmd.Add(deckCopy, PileType.Deck);` 本身通常只改数据，不保证有明显动画。

因此当前项目约定：

- 只要药水效果把牌加入 `PileType.Deck`
- 如果希望玩家看到明确反馈，就应显式补：
  `CardCmd.PreviewCardPileAdd(result, 1.2f, CardPreviewStyle.MessyLayout)`

也就是说：

- “加入牌组”是逻辑层
- “展示这张牌被加入牌组”是表现层
- 两者不要默认等价

### 新增药水时建议检查清单

每次新增 Karen 药水，建议至少确认下面这些点：

1. 是否继承了 `KarenBasePotion`
2. `Id.Entry` 是否稳定，且与资源命名一致
3. `images/potions/` 下是否存在主图和 outline 图
4. `zhs/eng` 的 `potions.json` 是否都补齐了
5. 是否已经加入 `KarenPotionPool`
6. 是否需要战斗内生成牌、选牌、复制到牌组
7. 如果有加入牌组行为，是否补了 `PreviewCardPileAdd(...)`

## 修改文本时要同步检查什么

每次改描述文本，建议顺手检查：

1. `CanonicalVars` 是否同步更新。
2. HoverTip 是否仍然准确。
3. 行内关键字显示是否会出排版问题。
4. 中文和英文版本是否都要同步。
