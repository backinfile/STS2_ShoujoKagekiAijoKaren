# 全特效首次使用准备与发布检查

## 范围与实现

按玩家要求，将普通闪耀的提前准备扩展到整个 Mod 的视觉资源。`KarenVfxCatalog.g.cs` 由 `tools/vfx/first-use/catalog.py` 生成，覆盖 68 个视觉节点类型（含辅助节点，不等于 68 段独立演出）、35 个共用资源所有者、158 条显式资源路径。完整目录扫描同时覆盖动态拼接路径所在目录，PackedScene 的原生材质/纹理/粒子依赖递归收集。普通/临界闪耀、耗尽、约定塔/移牌、攻击/命中、燃料、常驻、收益、舞台、选牌、能量、角色场景与影片均纳入准备体系。

- 原生主菜单资产加载完成后等待一次准备；原生开局预载提供兜底。资源加载、共用静态纹理/Shader 初始化、音频缓存、五种卡框轮廓和华恋能量轮廓均在首次交互前完成。RGBA8 alpha 扫描改用批量像素，其他格式保留原读取语义。
- 支持动态代码的运行时提前编译视觉方法，不调用方法体；AOT/不支持的后端保留资源准备路径。Android Mono 的具体表现仍需真机检查。
- 128×128 的独立 SubViewport 使用 Always 更新，分批绘制纹理、Canvas Shader 的几何/精灵/CPU 与 GPU 粒子变体，以及粒子处理材质；每批等待两次 `FramePostDraw` 并检查实际 draw calls。视频只在静音离屏播放器中短暂准备解码/上传，不触发正式剧情或 BGM。后续重新创建播放器仍可能有解码开销，不承诺所有手机驱动/解码器绝无首次长帧。
- 效果保留每次演出独立的动态材质与参数。共用生成纹理、续演调色/曲线/粒子处理模板在加载时准备；不改变节拍、伤害、移牌、确认收益或战斗 RNG。预热不执行演出工厂，也不播放可听音频。
- 本体 `AssetCache` 使用显式 Dispose，单纯持有 C# 引用不能保活。只对这批有界资源及依赖保留缓存，并将角色选择期间已标记漏载的条目从漏载清理集合中提升，其他资源按本体原逻辑清理。临时视口在成功/异常路径均释放；重复准备直接复用同一 Task。代价是首次加载增加准备时间及这些共用资源的常驻内存。

方案与 Godot 官方对首次编译和真实绘制的说明一致：[Godot 4.5 pipeline compilations](https://docs.godotengine.org/en/4.5/tutorials/performance/pipeline_compilations.html)。实际收益以测量结果为准；PC 的新进程不等于清空整个驱动缓存。

## 校验入口与证据边界

`AGENTS.md` 已要求工坊上传/APK 发布前主动运行覆盖检查、双版本首次/重复帧检查、资源有效性、生命周期和最终产物核验；APK 另需对应 ARM64 真机的新装/覆盖/冷启动/后台恢复。缺设备时只能标记测试候选包。工坊仍执行原有完整单人/同版本多人矩阵。

`release_check.py` 根据最终 Mod 的精确哈希，自动补跑两版 `all / bridge / shine / promise` 专项；全签名 APK 运行 12 项安装回归及完整解包。证据过期、漏资源、预热未绘制、资源被清掉、视口泄漏或首次明显长帧均不能直接算通过。失败退出码 1、缺真机/日志待审退出码 2、全部完成为 0。设备/矩阵摘要必须由真实结果整理，不能编造。

`all` 调用真实视觉工厂，29 组各首播及两次重复，检查原生普通/漏载缓存清理后资源有效、准备幂等及视口释放。它不替代逐牌规则/选牌交互/联机测试。`shine` 使用实际卡面，`promise` 使用实际入堆/归手，保存 MCP 前后截图和 `karen_check_hand`。计时窗口不截屏、不发起动作。

## 本轮结果

- 覆盖检查通过；临时加入未登记资源的负例被正确拒绝，移除后重新通过。
- 构建 Stable/Beta 的桌面及 Android AnyCPU 实现通过；新 APK 保持包名和签名，版本递增为 r4 / 10016。
- 首轮顺序塔桥：首次最大帧 17.42ms，重复约 16.74ms；比旧版已复现的 80–135ms 明显改善。
- 加入主菜单准备后普通闪耀：首次最大帧 16.70ms，重复 16.68ms；五种卡框几何完全一致。
- 原生漏载缓存提前 Dispose 的负例曾使回归失败，修正提升逻辑后资源有效性通过。
- 并行运行两版的首次探索出现不同位置的 36–50ms 零散长帧，部分重复播放也出现；原始失败记录保留，最终性能按顺序重测，不能删去失败数据或用并行结果宣称无卡顿。
- Android 真机及完整多人矩阵本轮未测；没有连接可用 adb 环境。用户手机首次入堆的最终效果仍需实际试用。

全览协议修订：最初的 all 工具每秒通过 MCP 查询进度，查询构建状态会干扰计时帧；这些结果保留为协议 1 的无效性能结论。协议 2 改为演出测完后写本地 JSON，外部只轮询文件，不在计时窗口请求 MCP。发布检查拒用协议 1 的 all 结果；bridge/shine/promise 原本就不在计时窗口持续查询。

最终正式版协议 2：29 组视觉工厂 × 3 次，首次最大帧范围 16.68–17.41ms；首次明显长帧判定均通过。准备 3815ms，297 个含依赖资源、29 批、445 次实际 draw calls；重复准备 0.0218ms。证据 `artifacts/vfx-first-use-20261022/runs/stable-20261022-165055`。

最终测试版协议 2：29 组 × 3 次，首次最大帧 16.68–17.48ms，整批同样没有 >33.3ms 长帧。准备 4011ms，297 个资源、29 批、445 次实际 draw calls，重复准备 0.0275ms。证据 `artifacts/vfx-first-use-20261022/runs/beta-20261022-165416/`。此进程在主菜单预热之后、开局原生预载时记录了一次 `Invalid Task ID`，不算日志全通过。
