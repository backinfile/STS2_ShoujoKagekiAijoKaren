# 全卡牌特效整理与分析（2026-09-28）

## 范围与结论

基于 `fab37b9721ff4d657bd544d2093aeb2fd92a2dbb` 静态审阅卡牌模型、关联 Power、命令、补丁、VFX 管理器和资源引用。本次只整理分析，不修改运行代码；按用户要求不进行完整测试，也未新增游戏内实测。下文的“代码事实”不等于画面已复现，“建议”不等于现有缺陷。

核心判断：当前已有完整的共用反馈基础，最值得先投入的是特效归属、坐标和生命周期的一致性，其次是关键机制触发的可读性；不需要给每张卡都做大型独占动画。

## 优先问题与证据

### P1：过去与未来光环可能被多个玩家共用

**代码事实，高置信度的归属缺陷。** [KarenPastAndFutureRingVfxManager.StartInternal](../../src/Core/PromisePileSystem/Vfx/KarenPastAndFutureRingVfxManager.cs) 遍历角色父节点的所有子节点，找到任意 `NKarenPastAndFutureRingVfx` 就重新 `Init(creatureNode)`，再存入当前玩家的缓存，没有 owner 过滤。

本体 `NCombatRoom.AddCreature` 的盟友节点挂在共享 `_allyContainer` 下（本机参考：`D:/Github/spire-codex/extraction/raw/src/Core/Nodes/Rooms/NCombatRoom.cs`）。第二个玩家进入该模式时，存在把第一个光环重新绑定给自己的明确路径；两份缓存还会指向同一个节点，停止其中一个会影响另一个。

建议实例显式绑定玩家或 Creature，复用时验证归属。最小验证：双 Karen 依次进入模式，分别脉冲、退出，另一人的光环不迁移、不消失。此次未进行双人复现。

### P1：最后的台词粒子发射源没有使用施法者

**代码事实，高置信度的归属缺陷。** [NKarenLastWordVfx.GetSourcePosition](../../src/ShoujoKagekiAijoKaren/GodotScripts/PromisePileSystem/Vfx/NKarenLastWordVfx.cs) 查找第一个 `Entity.IsPlayer` 的节点，而不是出牌者；调用也没有传入 Owner。单人时不易暴露，多人第二位角色出牌时可能从第一位角色身上发射。

建议将施法者或施法者节点贯穿播放入口与粒子创建，缺失时才使用屏幕回退坐标。最小验证：交换主客机和站位，分别触发文字演出，确认发射源。

### P1：燃烧与光环尚未统一角色变形策略

**代码事实，视觉影响待实测。** [NKarenBurnVfx](../../src/ShoujoKagekiAijoKaren/GodotScripts/PromisePileSystem/Vfx/NKarenBurnVfx.cs) 跟踪角色 `VfxSpawnPosition`，但生成范围仍使用 `PlayerWidth=240`、`PlayerHeight=320`。角色缩小时粒子不会自动缩成相同比例。

[NKarenPastAndFutureRingVfx.UpdatePlacement](../../src/ShoujoKagekiAijoKaren/GodotScripts/PromisePileSystem/Vfx/NKarenPastAndFutureRingVfx.cs) 根据局部 `Hitbox.Size` 计算半径，并保留至少 190 的半径；没有按角色全局变换缩放。这可能是刻意保持可读性，不能仅凭最小半径判定为错误，但需要与塔、角色尺寸建立一致的设计规则。

建议区分三种对象：贴身粒子随角色尺寸；地面光环保持朝上但半径适度变化；文字、计数保持正常阅读方向。角色水平翻转时，不应把文字镜像。上一轮塔变形修复只证明塔的专项结果，不能外推到所有持续特效。参考 [已有塔变形记录](promise-transform-2026-09-27.md)。

### P2：星光指引仍使用旧的角色上方落点

**代码事实，设计衔接问题。** [KarenStarGuide](../../src/Core/Models/Cards/shine/KarenStarGuide.cs) 启动本地专属演出后以跳过常规视觉的方式加入约定牌堆；[NKarenStarGuideVfx](../../src/ShoujoKagekiAijoKaren/GodotScripts/PromisePileSystem/Vfx/NKarenStarGuideVfx.cs) 使用角色位置向上 300，再叠加随机偏移作为落点，没有取塔坐标。非手牌的来源也使用屏幕下方回退位置。

因此代码表达的是“牌在头顶消失、塔逻辑更新”，没有明确的最终入塔段。建议保留金边与星群扩散，只把收束段接到塔锚点，区分手牌和抽/弃牌堆的来源。验证空集合、大批量、缩小、翻转、虚无模式，以及播放中离开战斗的清理。

### P2：觉醒形态的风场与 Power 生命周期分离

**代码事实，条件性风险。** 风场由 [KarenForm.OnPlay](../../src/Core/Models/Cards/neutral/KarenForm.cs) 启动；[KarenFormPower](../../src/Core/Models/Powers/KarenFormPower.cs) 的 `AfterApplied/AfterRemoved` 只处理音乐。风场停止入口目前由战斗清理调用。

这意味着中途移除 Power 的路径没有对应风场停止，单靠状态恢复也不会走卡牌 OnPlay。是否存在正常游戏中的具体触发路径，应单独确认。建议持续特效由状态应用、移除与恢复统一驱动，保持重复调用幂等。

觉醒风场是屏幕范围效果，不宜照搬“全部随人物缩小”的规则；其本地玩家限制也应视为明确的屏幕表现策略，而非直接判成多人漏播。

### P2：演出等待与快速模式需统一

**代码事实。** [KarenCarryingGuilt.OnPlay](../../src/Core/Models/Cards/shine/KarenCarryingGuilt.cs) 在舞台灯后执行 `Task.Delay(250)`，这是墙钟等待，不随游戏时间缩放，也不采用 Cmd.Wait 的 Instant 跳过逻辑。建议改用符合该演出目的的游戏时间等待。

**待验证风险。** [KarenLastWord](../../src/Core/Models/Cards/neutral/KarenLastWord.cs) 的伤害等待与 [视频节点](../../src/ShoujoKagekiAijoKaren/GodotScripts/PromisePileSystem/Vfx/NKarenLastWordVideoVfx.cs) 的独立播放生命周期不是同一个结束信号。Instant 下命令等待可被跳过，全局 UI 中的视频/文字是否在奖励界面残留，需要定向实测，不能仅凭静态代码下结论。

建议显式定义正常、快速、即时三档：伤害关键帧、可跳过部分、最长持续时间和战斗结束取消行为。不要一律替换所有 Task.Delay：例如虚无卡的延迟清理与罪过卡阻塞伤害的等待用途不同。

### P3：过去与未来抽牌声音有资源但未接通

**代码事实，是否恢复属于设计决定。** [PromisePileHooks](../../src/Core/PromisePileSystem/PromisePileHooks.cs) 中 `PastAndFuturePromisePileAudio.TryPlayNext(player)` 已被注释；存在对应管理器及 draw1–4 音频，但不能据此把轮播语音计入当前听觉表现。

建议先确认是否因重复播放或节奏问题而关闭，再决定恢复；若恢复，应限定触发、音量、多人本地策略和连抽节流。

## 表现投入建议

1. **先修正确性。** 光环按 owner 隔离、最后台词发射源、角色尺寸策略、持续状态清理和游戏时间等待。直接利用现有资源即可改善。
2. **再补机制因果。** 《旋转》伤害成长、《招架》格挡成长、《神圣星辰》入塔降费，目前对应钩子主要更新数值与日志。保留原生数字更新，再增加一次短促的数值/牌面提示，让玩家知道为何改变；避免每次移牌都长时间播放。《歌唱吧舞蹈吧互相争斗吧》已有牌堆加入预览，可补来源和接收者的短确认。
3. **最后拉开攻击层次。** 28 张攻击使用同类斩击，资源复用合理，但轻击、重击、多段攻击的节奏差异可以更清晰。优先《背靠背》的重击感、《神圣星辰》的两段节奏、《棒球》的主题命中；基础打击和低成本衍生攻击继续复用。
4. **控制大型演出数量。** 食物牌以治疗/力量等原生反馈加统一轻量提示即可；选项牌以选择确认和实际结果为主；诅咒、空壳不需要补主动演出。奖励类牌已有战后奖励或 Power 标记，应先检查可理解性，而非重复播大型动画。

性能方面，文字演出每 0.035 秒创建 7 个粒子、持续约 5.5 秒，估算单次累计约 1100 个粒子；这是代码数量估计，不是帧率或峰值实测。燃烧粒子还会创建材质实例。可在正确性修完后检查高频连打、重播、双 Karen 同屏下的节点数与帧时间，再决定共享材质或粒子池，暂不以静态推断要求重构。
